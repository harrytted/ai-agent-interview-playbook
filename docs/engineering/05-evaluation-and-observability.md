# 05 · 评测与可观测性

一次运行回复流畅、工具也返回成功，后台却多建了一张工单。要判断系统是否变好，需要检查业务终态，再把失败接回当时的检索、决策和执行记录。

本篇按“怎样算完成、分母怎么算、证据在哪里”来读。先遮住答案，给每个指标写出它能检查什么、漏掉什么，再做教学算例；优先级用于安排学习顺序。

### Q033 怎样判断一个 Agent 真正完成了任务？

**优先级：P0**

**30–60 秒回答：** 先把用户目标写成可检查的终态，再检查执行过程是否满足权限、时间和成本约束。工单 Agent 说“已创建”不算成功，要核对工单系统里的对象、字段和关联用户；问答 Agent 则检查事实与引用。把最终任务成功率、越权率、预算超限率分开报告，不能让高平均分掩盖一次严重越权。Agent 评测需要同时观察轨迹与环境结果，可结合程序、模型和人工评分器。[来源：Anthropic Agent Evals](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

**工程追问与权衡：** 多条工具路径都可能正确，强制匹配唯一工具序列会误罚有效方案；但金额、收件人、授权条件等约束应该确定性检查。评测环境要重置，否则上一次创建的对象可能替下一次“完成”任务。

**常见误区：** 把工具返回 HTTP 200、语言流畅、模型自评通过当成用户任务成功。

**微练习：** 为“找到退款政策并为符合条件的订单提交申请”写 3 个终态断言和 2 个禁止发生的副作用；明确需要哪些系统证据。

### Q034 成功率的分母怎么定义，拒答算成功还是失败？

**优先级：P0**

**30–60 秒回答：** 先固定任务集合、可处理范围和成功标准，再分别统计可答题正确完成、无证据题正确拒答、越权请求阻断，并报告每类样本数与覆盖率。若 100 个任务中完成 60 个、拒绝 40 个，只看已完成的 60 个，就像只给交卷的人算成绩：没交付的请求从报表里消失了。类比只说明分母遗漏；线上还要明确用户放弃、工具故障和转人工的口径。

**工程追问与权衡：** 单一“成功率”会诱导系统回避困难任务。可同时看总体完成数/全部有效请求数，以及已作答准确率；按任务类型、语言、租户、长尾难度分层，观察改进是否只发生在简单题上。

**常见误区：** 删除超时样本后再报成功率；把业务无权限的正确拒绝与检索失败的无答案混成一类。

**微练习：** 某集合有 80 个可答题、20 个不可答题；答对 64 个可答题，错误回答 6 个不可答题，其余 14 个不可答题均正确拒答，全部样本均有已判定终态。分别写出可答正确完成率、不可答正确拒答率和总体决策正确率。自检：80%、70%、78%。

### Q035 怎样构建评测集，避免越调越像“背答案”？

**优先级：P0**

**30–60 秒回答：** 从真实任务分布抽取脱敏样本，补充边界、故障和对抗案例。把用于改提示词的开发集与最终测试集隔开，并记录数据、提示、模型、工具和索引版本。相同工单的改写或同一文档的近重复内容应按组划分，时间敏感任务可按时间切分。反复查看测试错误后，它事实上已经参与开发，应再建立留出集。

**工程追问与权衡：** RAG 的知识库可以包含答案所需文档，这属于检索任务的正常设置；把测试问题与标准答案直接塞进提示或针对其手工修补规则则会扭曲结论。冻结测试集有利于比较，也要另设持续补充的生产回归集。

**常见误区：** 随机分行就认为没有泄漏；拿训练知识截止时间推断某条公开题一定没被见过。

**微练习：** 为 30 个来自 5 篇文档的问答设计分组切分方案，说明你要测的是“已知文档新问题”还是“新文档新问题”，两种目标不要混报。

### Q036 LLM-as-a-Judge 有哪些偏差，怎么用才可信？

**优先级：P0**

**30–60 秒回答：** Judge 也会判错，要先明确评分维度、锚定样例和可核对证据，再与人工标注对照。比如内容不变，只交换两个答案的位置，分数是否就翻转；控制无关长度差异后，是否仍偏爱长答案。评分器也需要一份考卷。MT-Bench 研究过位置、冗长和自我偏好等偏差，自己的任务仍需校准，不能直接套用论文结果。[来源：MT-Bench 论文](https://arxiv.org/abs/2306.05685)

**工程追问与权衡：** JSON 格式、金额、权限和数据库终态优先用程序检查；解释质量可交给 Judge。记录 Judge 版本和提示，抽查争议样本；同一个模型既生成又评分时，尤其要用外部证据和人工校准。

**常见误区：** 把 Judge 给出的 0.9 当成经过校准的 90% 正确概率；让 Judge 直接相信候选答案自述的事实。

**微练习：** 写一份“引用支持答案”的 0/1/2 分规则：0 无证据或矛盾，1 部分支持，2 全部关键断言被支持。给每档各造一个短样例，再盲评打乱顺序后的版本。

### Q037 一条有用的 Agent trace 应记录什么？

**优先级：P0**

**30–60 秒回答：** 用一次任务的标识关联规划、模型请求、检索、工具执行与最后结果；每一步记录开始结束时间、状态、输入输出摘要、错误类型和版本。Trace 把跨组件操作串成因果链，span 表示其中一段工作。[来源：OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/) 默认只保留排障必要元数据，敏感正文按权限、脱敏和保存期限管理。模型不可见的内部推理不是排障前提。

**工程追问与权衡：** 并发工具要保留父子关系或关联关系；失败样本提高采样率，但总体延迟统计不能直接拿有偏的 trace 样本计算。GenAI 字段约定会演进，接入时核对当前规范，不把自定义字段称为标准。

**常见误区：** 只保存最后回复，无法区分“没检索到”和“检索到了但没使用”；把完整凭据或个人信息写进日志。

**微练习：** 为一次“检索→重排→回答”画 4 个 span，标明根 span、父子关系、哪一步错误、应保留的 3 个版本号。

### Q038 怎样解释 p95 延迟，如何定位慢任务？

**优先级：P0**

**30–60 秒回答：** p95 描述指定样本窗口与口径下，约 95% 观测值不超过的延迟，不能当作平均延迟。先明确测的是排队、首字还是任务完成，再沿 trace 拆出检索、模型、工具及重试的关键路径。两路资料都必需时，快的那路先回来，用户仍要等慢的那路，因此并发总耗时不能简单相加。超时和取消也要单列，避免它们从统计中消失。

**工程追问与权衡：** 对同一批请求，不能用“每个组件 p95 相加”准确得到整体 p95。可用任务 trace 找慢请求集中在哪类路径，再评估减少串行调用、缩短上下文、缓存或并发是否伤害正确性。

**常见误区：** 首 token 快就宣称任务快；拿十个样本的 p95 给出稳定生产结论。

**微练习：** 两个独立必要工具分别耗时 0.8 秒、1.6 秒，合并耗时 0.2 秒。忽略调度开销，串行与并发分别需多久？自检：2.6 秒、1.8 秒；再解释为什么这不是线上 p95 的预测值。

### Q039 怎样算 Agent 的成本，优化时看哪些指标？

**优先级：P0**

**30–60 秒回答：** 按每次任务累计全部模型输入输出、检索/重排服务、工具、运行资源和失败重试成本；价格使用实际供应商账单口径和当时版本。除了每次请求均价，还看“总成本/成功完成任务数”，因为便宜但经常失败的方案可能更贵。记录循环轮数和上下文增长，再通过减少无效步骤、选择合适模型与缓存优化，并在同一评测集验证质量。

**工程追问与权衡：** 缓存命中也可能有计费；需要租户和权限隔离、内容版本与过期策略。长上下文让后续每轮重复携带历史，成本增长取决于实际输入策略，不能笼统说所有 Agent 都严格二次增长。

**常见误区：** 只算最后一次模型输出；用过期单价承诺实际费用；把减少工具调用本身当成成功。

**微练习：** A 方案 100 次任务共花 10 个计费单位、完成 80 次；B 花 8 单位、完成 50 次。每个完成任务分别为 0.125 和 0.16 单位；说明还需哪些质量和风险约束才能选型。

### Q040 离线分数提升，为什么线上还可能变差？

**优先级：P1**

**30–60 秒回答：** 离线样本、用户行为和线上环境可能不同：新资料、权限、并发、工具故障和用户中途改意图都能改变结果。先做可回滚的小流量发布，分别监测任务完成、转人工、用户纠正、延迟和成本，保留版本对照。线上点赞有选择偏差，不能单独证明事实准确；未随机分组的前后对比也可能受到流量变化影响。

**工程追问与权衡：** 样本量不足就报告观察窗口、数量与不确定性。把真实失败脱敏后加入回归集，再检查修复是否引入新问题。用户满意度与业务终态冲突时，要回到具体产品目标解释。

**常见误区：** 离线分数提高几个点就说业务转化提升同样幅度；把相关性写成因果提升。

**微练习：** 为一个新检索器写发布门槛：1 个主要质量指标、2 个保护指标和 1 个回滚条件。阈值由你设定并标为实验目标，不写成行业标准。
