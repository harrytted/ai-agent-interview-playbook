# 17 · 事件驱动与主动任务面试题

对应学习章：[17 · 事件驱动与主动任务](../../advanced/17-event-driven-and-proactive-agents.md)。本页收录Q105–Q107，讨论触发、投递、对象版本与授权，重点是用户没有发新消息时，系统怎样有界地接受下一项工作。

### Q105 事件ID、业务意图ID和运行ID分别解决什么问题？

**优先级：P0**

**30–60 秒回答：**

事件ID标识来源的一次事件，用于识别网络重投；业务意图ID标识同一项用户目标，例如某订阅对政策v3的一次复核，避免不同事件重复建立相同业务；运行ID标识实际执行，便于追踪和恢复。三者不能互换。宿主应保存事件内容指纹，用唯一业务意图接受任务，固定输入并核对参数。恢复后可以有执行尝试，但不应随意换意图键再制造对象。记录已接收不等于任务已完成，Outbox存在也不等于外部消息已送达。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

**事件（event）**是来源发生变化的记录；**业务意图（intent）**是用户授权范围内希望完成的工作；**运行（run）**是系统执行该工作的实例。把三类标识分开，才能回答“这是不是同一条投递”“是不是同一件业务”和“哪次执行产生了结果”。

政策来源发送`e203`，接收器处理后尚未确认就断开，来源再次发送`e203`。此时应通过事件ID和内容指纹找到账本中的处理决定，不能再扣预算。若相同事件ID换了正文，属于冲突；将其当作普通更新覆盖会破坏审计。事件内容指纹用于核对同一标识的内容一致性，不能代替来源认证。

另一个来源记录`e204`也指向同一个政策v3。只按事件ID检查会认为它是新工作，因此还需定义业务意图：本例采用订阅ID、对象ID和政策版本。派发时用意图唯一键接受任务，将可信用户、输入版本与正文一起保存；相同意图对应不同参数时应报冲突或要求显式新版本，而不是静默复用结果。

运行ID解决执行追踪：某运行何时开始、读取什么条件、在哪步等待、用了多少预算。服务可以沿同一任务恢复，也可以按明确定义建立新的执行尝试；无论采用哪种方式，业务副作用仍需关联稳定意图。每次重试都换意图ID，等于把取件凭条换掉后再领一遍，原来的去重就失去作用。

本地实验在SQLite事务中写入任务、预算和本地Outbox，用意图唯一键防止重复接受。与16的HTTP任务服务对接时，意图ID映射到接受幂等键，运行ID映射到执行记录，事件ID保留为因果来源；不能把三个字段压缩成一个随机UUID后声称已经解决重试一致性。实验的`accepted`只是登记状态，后续复核和通知送达仍需各自证据。

**常见追问：**

1. **两个事件ID不同，就一定是两项业务吗？** 不是。它们可能重复报告同一对象版本；需用对象版本和业务意图判断是否新增任务。
2. **事件哈希能代替签名校验吗？** 不能。哈希帮助发现已记录内容被改变，不证明发送者是谁；真实Webhook应先核实来源与签名。
3. **恢复时新建run_id会破坏幂等吗？** 不必然，关键是业务意图与操作键仍稳定，恢复路径能查询已有任务和对象；不能用新运行ID绕开业务查重。

**实战案例：**

教学订阅s1复核`policy-hailan:v3`，事件e203接受任务后确认丢失。重启后收到e203重投，再收到不同ID的e204报告同版同文。正确结果是接收账本保留投递决定，但任务、预算扣减和本地通知都只有一份。再发送同ID不同条文，系统应拒绝冲突；测试改用v8、800元和新标识，证明逻辑依赖合同而非固定答案。

</details>

**常见误区：**

按事件ID去重就宣称业务恰好一次；所有重试换随机业务键；只保存“已收到”而不保存处理决定；把运行正常结束当作业务已完成。

**微练习：**

运行`python3 examples/event_agent_lab/lab.py --scenario crash_recovery`，查看账本、任务、预算和Outbox快照。再运行`duplicate`，解释同ID重投与不同ID同版为何都不新增任务，写出三类ID及它们各自不能证明的事情。

### Q106 重复、乱序和迟到事件怎样收敛而不覆盖新状态？

**优先级：P0**

**30–60 秒回答：**

先区分投递重复和业务重复：事件ID加内容指纹识别重投，对象版本与意图键防止重复工作。对于单一可信来源的递增版本，先到v3再到v2应保留v3；同版不同内容记录冲突。短时频繁变化可以按目标去抖合并，派发前再次核对订阅、版本、授权和预算。状态、任务接受与Outbox在适当事务边界持久保存，确认丢失后重投查账本恢复。事件时间、处理时间和制度生效时间不同，不能用最后到达或服务器时间代替业务版本。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

**至少一次投递**意味着同一事件可能多次送达，处理者需要能够安全重放。**乱序**是到达顺序与来源顺序不同，**迟到**是事件超过通常预期时间才到达。三者可以同时出现：一条旧事件因重投晚于新版到达，不能靠“收到就是最新”处理。

实验先核对事件ID与指纹，再比较对象递增版本。v3先到时保存v3；v2后到只记录`stale`决定，不覆盖对象，也不派发旧版复核。同版同文在没有冲突时保持安静；同版不同文会持久隔离该版本并清除尚未派发项，同版重投不能解隔离。等待可信更高版解决后再建立新版本复核候选，即使正文回到原值也不跳过。已接受任务和既有Outbox不会在本实验中被追溯撤回，需另走服务取消或补偿合同。该比较成立的条件是来源为同一对象提供可比较版本；多来源并行编辑或分支合并需要更明确的版本或冲突合同，不能把任意时间戳当成全序。

事件时间反映来源的发生记录，处理时间反映接收器何时处理。制度还有生效日期，回答历史差旅时可能正确使用旧政策；这和当前事件归并是不同问题。接收器可保留新版本，知识检索仍按业务日期选择适用版本。把新旧资料全部覆盖删除会破坏历史查询，即使事件顺序处理正确也不够。

**去抖**等待一个安静窗口，适用于“对最新状态进行一次复核”的目标。v2在0秒、v3在2秒到达，窗口5秒，则7秒派发一次v3工作。待派发项需持久保存，派发时重查有效订阅与预算。若目标是审计每一笔付款，合并成最新一笔会丢业务，不应套用同一策略；调度技术必须服从任务语义。

中断恢复还要处理确认边界。本地先提交对象与待派发项，派发事务原子保存任务、预算和Outbox，再记录输入确认；若在确认前模拟故障，重投沿账本补记确认，不再接受任务。本例只证明本地数据库内的效果，外部发送器仍可能重复投递，需要渠道或接收端的独立幂等合同。

**常见追问：**

1. **版本越大就必然对当前问题适用吗？** 不一定。版本归并保证当前对象不倒退，制度适用还受生效日期、人员类别和查询日期约束，应连接知识生命周期规则。
2. **去抖后只剩最新事件，审计记录是否也应删除？** 不应混为一谈。可以保留原始事件与处理决定，只合并派生工作；审计和任务调度有不同保留要求。
3. **所有迟到事件都丢弃吗？** 不是。可以忽略其当前状态更新，但保留来源、处理决定或进入补偿/审计路径；是否重新计算历史结果由业务合同决定。

**实战案例：**

系统先收到政策v3“750元”，随后收到v2“700元”，用户又在去抖窗口内取消订阅。正确结果包括：对象保留v3；v2记为旧版；未派发项被清除；后续晚事件不能创建新任务。若v3内容后来被来源同版改写，记录版本冲突而不静默替换。验收同时查对象版本、接收决定、待派发项和任务数，单看日志中出现“ignored”不足以证明数据库没倒退。

</details>

**常见误区：**

用到达时间覆盖版本；把去抖当成所有事件都能丢；只测试重复而不测试同版冲突；重启清空预算；声称Outbox等于外部恰好一次送达。

**微练习：**

分别运行`out_of_order`、`debounce`和`cancelled`。手画0、2、6、7秒的待派发版本与任务数，再把版本改成9和8。验收解释为什么第6秒不能派发、旧版不能回写，以及取消对待派发与已接受任务的边界。

### Q107 主动任务怎样分离触发条件、执行授权与通知条件？

**优先级：P0**

**30–60 秒回答：**

触发条件决定何时产生候选工作，执行授权决定可信用户允许哪些业务动作，通知条件决定是否值得以及能否发送结果。三者单独检查，事件和模型都不能自行授予权限。有效订阅仍需对象匹配、动作授权、预算和停止条件；通知可以要求有实质变化且附正式条文。取消订阅清除待派发项，派发前复查；已接受任务和外部副作用另走取消与核对合同。主动不代表无限后台运行，无变化应安静，预算耗尽和循环应有明确终态。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

**触发合同**说明系统为什么现在开始工作，例如某用户订阅对象的新政策版本，或指定时间进行一次复核。它应包括订阅范围、来源、有效期、预算和取消方式；“有新消息”“模型认为值得做”都不足以表达完整边界。

第一道检查是触发资格：订阅是否仍有效、事件对象是否匹配、版本是否需要处理。第二道是业务授权：可信身份是否允许接受复核任务、读取相应资料，以及是否允许受保护写入。订阅住宿政策变化通常只授权读取、比较或准备草稿，不包含批准报销、付款或向所有员工发送消息。外部事件载荷与模型生成内容都不能修改这份授权。

第三道是通知条件：有实质变化吗，影响哪些用户，正文能否给出正式条文、版本与适用范围，目标渠道是否在授权内？可以允许复核但不通知；也可以允许本地提醒而不允许发邮件。实验以正文相等作为无变化判定，是可复算的简化，实际业务还需比较日期、适用对象和权限等字段。

系统自身回写可能再次触发同类事件，造成自激循环。需要来源或因果标识、事件类型过滤、去抖、最大派生深度和持久预算等合适组合。实验实际实现可信本地来源过滤和每订阅接受任务数上限；这不是通用分布式循环识别。停止决定和累计消耗应在数据库中保存，不能进程重启后重新领预算。

取消订阅应阻止未来派生任务，并清除待派发项，派发时再检查状态。若任务已经接受，是否连同在途查询、草稿和已提交对象一起停止，必须另定义并连接任务服务。本地Outbox的`local_pending`只能报告通知意图存在；未经外部渠道验证，不能说“已通知用户”。

**常见追问：**

1. **用户说“政策变化提醒我”，可以自动批准受影响申请吗？** 不能。提醒与业务批准是不同动作，需独立授权；发现异常可以准备复核草稿并等待后续决定。
2. **允许执行复核，就一定要发通知吗？** 不是。没有实质变化、用户要求安静或渠道不在范围内，都可能执行后不建立通知对象。
3. **取消订阅能保证已提交外部动作被撤销吗？** 不能。它控制后续触发，外部动作是否发生、是否可撤回及如何补偿需按服务合同核对。

**实战案例：**

同一政策事件匹配两个订阅：甲仍订阅但复核权限被撤回；乙允许复核但关闭通知。正确结果只有乙的一项任务，甲不产生任务，两者都没有本地通知。随后预算耗尽，再有新版也只更新政策状态并记停止原因；内部回写事件不继续派生工作。测试应核查用户归属、任务数、预算和Outbox，而不是只测试一个“是否触发”的布尔值。

</details>

**常见误区：**

订阅等于无限授权；事件来源标签等于来源认证；无变化仍周期发送状态；用通知开关控制业务权限；取消后把历史账本和已执行对象一并删除。

**微练习：**

运行`authorization`与`budget_and_loop`，再阅读独立测试中的`trigger_permission_and_notification_are_separate`。列一张三列决策表，分别回答“是否候选”“是否接受任务”“是否建立通知”，并指出每项决定由什么可信状态提供。
