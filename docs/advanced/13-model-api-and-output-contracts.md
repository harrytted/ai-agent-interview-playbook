# 13 · 模型API与输出合同面试题

对应[学习章13：模型API与输出合同](../../advanced/13-model-api-and-output-contracts.md)，本组Q093–Q095从输出约束走到真实流的完整性。重点是接收方凭哪些事实推进，而不是记住某个SDK的方法名。

### Q093 提示要求JSON、JSON模式与Schema约束输出有什么区别？

**优先级：P0**

**30–60 秒回答：**

提示要求JSON是行为指令，不保证每次满足；JSON模式的具体保证依供应商接口，通常关注语法；Schema约束进一步限制受支持的字段、类型与取值。三者都不能证明金额来自实际证据、对象属于当前用户或业务动作已经完成。我会先解释本接口的输出能力与例外，再在宿主分别校验结构、业务语义和授权，把拒答、截断与正常结束分开处理。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

JSON规定数据表示的语法，Schema描述接收方期望的数据结构与约束。提示“不要输出Markdown”可能减少格式错误，却不能替代机器校验；合法JSON也可能只是一个数值。接入新接口时先核对支持的Schema子集、字段配置位置、模型及协议版本，不能照搬另一家接口的参数名。

假设答案应包含两条`claims`，每条有city、limit_cny与reference。结构校验可以拒绝字符串金额或缺字段；它不能判断7000是否符合实际条款，也不能证明reference真在本轮取得。宿主需把主张与可见观察对应，校验适用城市、日期、金额和来源，并检查两地问题是否只答了一地。

约束输出也要处理终止分支。当前Claude结构化输出文档说明拒答和token上限可能改变预期输出；HTTP 200与收到文本不构成成功证明。不要先盲目解析业务对象，再把所有异常混成“格式错了再试”；先读取终止原因，按合同决定是否可解析、重试或转交。

还应将错误归到正确的修复层：JSON无法解析检查语法和完整性；字段缺失检查结构；未知Schema关键字检查供应商支持范围；引用存在但不支持断言检查证据。改变采样或重复请求并不能补上缺失的业务资料。本题诊断的是“哪项保证失败、应由谁修复”，完整解析状态另见[学习章的状态表](../../advanced/13-model-api-and-output-contracts.md#一次响应要保存哪些解析状态)。

执行工具还有另一层边界。参数满足Schema后仍须验证可信身份、对象权限与业务状态；写入完成后读取真实对象。原理可回查Q027；本题新增的是模型输出能力与响应生命周期，不能只重复“Schema不够”一句话。

**常见追问：**

1. **Schema里有金额上下限，是否就无需查条文？** 不够，实际上限可能随城市、员工类别与生效日期变化，需核对当前任务证据。
2. **拒答也是HTTP 200，网关是否应该记成功？** 可记HTTP传输成功，但任务应单列拒答；它不进入已完成业务任务分子。
3. **供应商宣称约束输出后还要宿主校验吗？** 要核对实际支持范围与例外，并继续检查业务事实、授权和最终对象，格式能力不承担这些职责。

**实战案例：**

两地制度回答返回合法JSON，海岚金额却是7000，云洲650。宿主读取本轮条款后确定海岚为700，拒绝交付错误主张，保留原响应与错误阶段。验收改变条款ID和城市后仍能检测不一致，不能让校验器只检查硬编码的700。

</details>

**常见误区：**

把合法JSON当成正确业务对象；用生成格式保证授权；把拒答或截断自动当成普通答案重试；混用不同供应商的Schema参数。

**微练习：**

运行 `python3 -m examples.model_protocol_lab.lab --scenario semantic-error`。指出语法、结构与事实哪层失败，再把观察与主张同时改成新城市815元：正确版本应通过，沿用旧金额的版本应失败。

**学习与参考：** [学习章13](../../advanced/13-model-api-and-output-contracts.md) · [协议实验](../../examples/model_protocol_lab/README.md) · [Claude结构化输出](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)。

### Q094 一次响应包含多个工具调用时，怎样按ID完整回填？

**优先级：P0**

**30–60 秒回答：**

先保存完整assistant消息，再用每个工具调用ID建立待办；宿主验证工具、参数与权限后执行，成功或失败观察都绑定原ID。收到全部结果后检查请求ID与返回ID一一对应，拒绝缺失、重复或陌生ID，再按供应商合同组织下一次输入。返回顺序可以不同，不能按数组位置猜对应；模型提出调用也不等于工具已经执行。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

本题讨论应用执行的client tools。一次模型响应可以同时包含文本和多项工具请求，调用ID是工具往返关联键；内容块索引用于流式组装，二者不应混为一谈。服务端工具的生命周期另有供应商合同，不能统一套用“全部由宿主执行”。

给定请求ID为`[call-1,call-2]`，先对下面的回包作判断，再讨论如何组织消息：

| 实际结果ID | 是否可直接进入下一轮 | 诊断 |
| --- | --- | --- |
| `[call-2,call-1]` | 可，仍需核对实际结果合同 | 倒序不影响按ID关联 |
| `[call-1]` | 否 | call-2尚无观察，不能让模型补造 |
| `[call-1,call-1,call-2]` | 否 | 集合相等但不唯一，单纯转成set会漏检 |
| `[call-1,call-3]` | 否 | 既缺call-2，又混入陌生ID |

检查要同时覆盖完整性与唯一性，而不只比较集合。宿主验证工具、参数和读取资格后执行，合法工具错误按协议返回明确错误观察；资料为空、读取失败和结果未到不能混成一个空字符串。正常完整往返见[学习章13](../../advanced/13-model-api-and-output-contracts.md#本地实验完整工具往返与结果校验)，这里重点是从异常回包反推哪项合同被破坏。

保留完整assistant块和对应工具结果，可以解释模型为什么接着回答。只保存最终文本，会丢失工具请求和执行之间的证据。恢复前还应核对当前可见性；原政策live适配器在历史证据被撤回时停止旧会话回放，避免保留的assistant文字再次带回受限内容。

调用对应的作用域也要明确：消息index定位块，响应/运行身份加call ID定位一次往返，业务意图定位受保护动作。模型重试后以call-9提出与先前call-1相同的写入，不代表另一项已授权业务；反之，两次金额不同也不能因工具名相同而静默去重。需要独立的业务键和参数指纹核对，不从call ID推断业务幂等。[对应边界](../../advanced/13-model-api-and-output-contracts.md#调用身份与工具结果的对应)

**常见追问：**

1. **结果倒序返回要重跑吗？** 不用，只要ID完整且唯一即可重新排列；无真实数据依赖的读取还可以并行，但预算与权限仍由宿主管理。
2. **一个工具失败，其余成功，怎样回填？** 按实际合同给失败项明确错误结果，保留其他观察；是否有限重试由错误类型与剩余预算决定，不能漏掉该ID。
3. **同一ID能否在重试中用于另一组参数？** 应按合同拒绝冲突，不能靠复用标识掩盖新意图；业务写入还需独立稳定operation ID及幂等合同。

**实战案例：**

旧实现先将结果转为字典，重复ID覆盖了较早观察，后续集合检查仍通过。修正为在覆盖或去重之前检查原始结果的重复、缺失和陌生标识，再保存按ID关联的实际结果。验收同时包含倒序合法与重复非法两类输入，避免“自动整理顺序”悄悄变成“自动丢弃冲突”。

</details>

**常见误区：**

按位置对应；只取第一个tool_use；工具失败就悄悄不回包；重复执行整个批次来补一项失败；把call ID当成跨系统业务幂等键。

**微练习：**

运行normal、missing-result和duplicate-id三个场景，比较 `result.json` 与 `next_request.messages`。合格答案指出哪两个变式不能进入下一轮，且能解释倒序回包为什么仍合法。

### Q095 收到半截参数或发生断流后，怎样判断响应是否完整？

**优先级：P0**

**30–60 秒回答：**

分开检查网络字节、SSE事件、内容块和整条模型响应。用增量UTF-8解码器保留未完成字符的字节，按行与空行派发SSE，再按块索引累加工具参数；只有响应完成、结束原因允许且完整参数通过校验，才能调度。max_tokens是截断，refusal是拒答，缺message_stop的EOF表示响应不完整；网络关闭和收到右花括号都不能单独证明任务成功。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

流式传输缩短可见输出等待，却没有把内容自动变成完整业务动作。一次read可能停在中文UTF-8字节中间，也可能包含两条SSE事件；分块大小属于网络实现。正确解析应逐层保留残留数据，不能把read边界当作JSON边界。

SSE用字段行和空行分隔事件，多条data行拼成事件数据；事件数据再表达供应商的消息与内容块。工具input_json_delta里的partial_json仍是一个字符串片段，先累加到对应块，再解析完整对象。即使某一段已经能解析，也可能只是完整参数的前缀，不能提前执行。

结束判定独立进行。块已停止但消息未完成，不能凭局部块宣布成功；max_tokens要停止不完整调用，refusal独立记录，缺终止事件的EOF记为不完整或传输失败。完整end_turn后仍需业务验收；终止模型生成与完成用户目标是两个结论。

断流后重试尤其要看副作用阶段。如果还没调度工具，可以按模型请求策略重新获取；若工具已派发而确认丢失，应沿操作ID核对真实结果。把整轮重跑容易重复创建工单；停止本地等待也不保证远端工作已取消。

**常见追问：**

1. **已经看到完整JSON但还没有结束事件呢？** 保留为候选内容，继续等待协议终止或期限；完整JSON不构成正常结束证明。
2. **半个UTF-8字符出现在连接末尾怎样处理？** 增量解码器在EOF最终校验失败，记录传输不完整，不用替换字符凑出合法业务参数。
3. **为什么SDK仍需要应用知道这些边界？** SDK可重组事件，但何时执行、怎样计预算、异常后是否可重试以及是否已产生副作用仍属于应用合同。

**实战案例：**

“海岚”的一个字符被拆成两次读取，参数JSON又被拆成三项delta。旧实现逐块json.loads而失败；修正后保持解码器、SSE缓存与块缓存，逐层完成。验收枚举每个可能的两段字节切分，结果一致；再删message_stop，必须报告transport_failed且不派发工具。

</details>

**常见误区：**

把网络分块当JSON；拼错不同块的参数；看到右花括号就执行；用HTTP 200抹掉拒答或截断；断流后无条件重跑副作用。

**微练习：**

先判断三份事件序列：①尚未start块1就收到其delta；②块0已stop后又收到其delta；③所有块结束，先收到带stop_reason的message_delta，再收到仅更新usage的message_delta，最后message_stop。在本地子集里前两项拒绝，第三项可完成；若第二次重复给出非空stop_reason则拒绝。再运行truncated、refusal、disconnect，核对“非法转移”和“合法前缀但未完整结束”的区别。状态图见[学习章](../../advanced/13-model-api-and-output-contracts.md#一次响应要保存哪些解析状态)，这些手写序列是诊断题，不冒充新增实验场景。
