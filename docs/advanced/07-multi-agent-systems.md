# 07 · 多 Agent 系统面试题

对应学习章：[07 · 多 Agent 系统](../../advanced/07-multi-agent-systems.md)。本页收录 Q075–Q077，依次讨论控制权、共享状态，以及协作的停止与成本。

三位研究 Agent 各自交卷，报告却用了三种统计口径，面试官会接着问：谁该负责统一？分工能减少独立工作的耗时，也会增加“开会”成本；本组题先把控制权和证据合同说清。

### Q075 什么时候采用 Manager，什么时候采用 handoff？

**优先级：P0**

**30–60 秒回答：**

先看谁负责下一步和最终答复。**Manager（主管调度）** 把专家当作有边界的能力调用，拿回结果后继续汇总；**handoff（控制权交接）** 让另一角色接管当前交互，继续向用户收集信息。独立上下文能减少过程信息进入主会话，却不自动隔离权限。我会先做单 Agent 基线，再根据任务独立性、上下文负担和交接成本决定分工，并给每次交接定义输入、产物、权限和返回条件。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

先把“需要更多知识”和“需要改变交互负责人”分开。政策比较由一个协调者统一交付时，可将地区研究交给专家，专家完成后返回结构化证据，协调者继续判断。用户从政策咨询进入申请办理，需要专员连续收集字段时，handoff 更自然。判断依据是控制权和对话责任，不能仅数模型实例；同一运行时通过持久状态切换提示与工具，也能实现交接。

委派前写清任务合同：原始目标、已确认事实、资料版本、可用工具、资源范围、剩余预算、需要返回的字段，以及何时报告缺口。专家结果至少包含结论、来源、适用条件和执行状态。协调者要能区分“已核对”“待补证”“工具失败”，避免把语气肯定当作任务完成。只给专家一个地区名称，通常不足以保证比较口径一致。

handoff 还要定义谁接收后续用户消息、哪些状态被保留、何时交回。交接摘要可以传递已确认事实，却不能把推断写成用户授权。申请专员接管对话后，提交仍需检查当前身份、对象权限和具体批准。控制权像值班安排，权限像门禁；换了值班人，门禁不会自然升级。

取舍要通过固定任务比较。独立研究可以并行，也能隔离中间工具输出；代价是多一次模型调用、摘要损失和协调延迟。简单的一次查询通常不值得拆成会议。先记录单 Agent 的失败类型，再用相近预算比较专家模式；如果收益来自更多尝试，应把预算差异一起展示。

**常见追问：**

1. **子 Agent 有自己的循环，仍算工具模式吗？** 可以。内部多步执行不改变外部控制合同；若完成后回到主管，由主管决定答复，仍是主管调用专家。
2. **上下文隔离能防止专家越权吗？** 不能。还需限制执行器凭据、工具集合、存储命名空间和资源权限；少看消息不等于少拿权限。
3. **专家失败时主管应直接换一位吗？** 先按错误类型处理。暂时读取错误可有限重试，缺证据需补资料；盲目换专家可能重复同一缺口并消耗预算。

**实战案例：**

教学案例中，主管比较两地差旅政策，另有申请专员。若两位研究专家直接和用户交谈，会重复询问出差日期。处理时让主管持有已确认日期，向专家发送相同口径；只有用户进入申请流程时才 handoff。验收检查研究结果都带同一日期与来源，申请专员能继续补字段，同时系统中没有未经批准的提交对象。

</details>

**常见误区：**

把不同提示词数量当作协作能力；给专家一个“只读”角色名就认为权限已限制；把交接摘要里的“建议提交”误当成用户批准。

**微练习：**

为“查政策→比较→申请”画两种控制流，各写交接输入、输出与终止条件。验收要求指出谁负责最终答复，明确一个应使用 Manager、一个应使用 handoff 的转折，并给出单 Agent 比较基线。

### Q076 动态任务图怎样处理共享状态、冲突与迟到结果？

**优先级：P0**

**30–60 秒回答：**

我会为任务节点设置稳定 ID、计划版本、依赖、预算和完成条件。结果返回时核对节点与版本，重复结果去重，旧计划结果不能覆盖新状态。共享证据可追加，最终报告由明确的所有者写入；Reducer 只定义数据怎样合并，不负责判断矛盾事实。重规划会生成新图，但节点循环、重规划次数和整个任务仍分别受停止规则约束。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

**任务图**把子任务表示为节点，把先后或数据依赖表示为连线；**动态任务图**允许根据新信息修订这些安排。**Reducer（归并函数）** 规定共享字段如何接收多个更新，例如去重后追加证据。它规定数据怎样合并，不会替协调者裁决事实。

动态规划不是每次想到新步骤就随手追加一个任务。先给当前计划一个版本，为节点记录稳定身份、前置条件、输入资料版本、产物合同和状态。调度器只有在依赖满足、预算已预留、并发名额可用时才派发。这样一个节点的“完成”才有可核对含义，恢复后也能识别它是否已经执行，避免仅凭一段聊天记录重新安排所有工作。

新证据要求改变依赖时，先更新计划版本，再决定保留、失效或重跑哪些节点。例如统计口径从申请数量改成申请比例，旧数量结果仍可作为原始证据保存，但不能继续当作新比较结论。结果消息应携带任务与计划版本；迟到消息进入明确的归档或复核分支，不能按最后到达覆盖当前报告。

共享状态需要字段级所有权。研究分支可以追加带来源、版本和片段 ID 的证据；协调者负责最终综合。Reducer 可以实现追加、集合去重或特定覆盖规则，却不了解金额为何冲突。两个来源分别适用不同日期时，正确处理是保留证据并核对条件，而非用最大值、最新到达值或模型多数票替代事实判断。

DAG 只约束这一版节点之间的有向依赖，节点内部仍可能调用工具循环，重规划也可能反复产生新图。因此要分别限制节点步数、总重规划次数和全局预算。并行增加后还需背压：汇总方或下游服务处理不过来时暂停新派发。任务图负责“先做谁”，共享状态负责“保存什么”，两者都不能代替资源控制。

**常见追问：**

1. **旧版本结果都要删除吗？** 不必。可保留来源与执行记录，供复核或重新计算使用；关键是不能未经验证进入当前结论。
2. **追加列表天然幂等吗？** 不是。同一消息重送会追加两次，应按稳定结果 ID 或来源版本加片段 ID 去重，并定义冲突处理。
3. **所有节点都成功就能成功交付吗？** 仍要验收综合结果。节点可能采用不同口径，或汇总遗漏必要限制；任务终态应由整体验收条件决定。

**实战案例：**

教学案例先比较三地申请量，随后发现各地申请总量差异很大，计划升级为按比例比较。一个旧 Worker 晚到并写出“北湾增长最多”。处理时保留旧计数证据，阻止它覆盖新版比较，补齐分母后重新综合。验收注入同一结果两次及旧版本结果一次，当前报告应只使用新版口径，证据集合无重复，旧数据仍可追溯。

</details>

**常见误区：**

把 Reducer 当成事实裁判；把 DAG 无环误解为整个 Agent 不会循环；重规划时不更新版本，导致迟到结果悄悄修改新结论。

**微练习：**

写一张含三路研究和一次综合的节点表，再注入重复、迟到和矛盾结果。验收要求分别给出处理状态，不覆盖新版结论，并展示节点循环与整项任务的两个停止条件。

### Q077 多 Agent 怎样在失败、取消和高成本时收敛？

**优先级：P1**

**30–60 秒回答：**

先按分支状态处理，不能把读取失败、证据冲突和完成混成一个成功。有限重试服从主任务预算与期限；取消后停止新派发，通知运行中分支，对已经提交的外部动作继续对账。判断是否值得多 Agent，要在同题、相近预算下比较最终质量、延迟与费用，并做消融。**多个角色互相赞同不代表独立验证**，仍需原始证据和校准过的评审。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

先建立可区分的分支状态：完成、可恢复读取错误、缺证据、需要澄清、取消中、结果未知等。协调者依据状态推进依赖，而不是等每位角色都发一句“完成”。暂时网络错误可以有限重试；政策条文互相矛盾需要核对版本，继续重复相同搜索不一定增加信息。允许部分交付时，要记录缺口；若完整比较是硬要求，则不能改口宣布完成。

全局预算与截止时间要传到各分支。派发前预留，已产生费用需结算，重试不能重新获得一整套额度。下游限流时减少在途请求并停止无关探索。集中协调方便管理这些控制，也会成为调度瓶颈；跨服务自治有价值时再采用更多去中心机制，同时付出重复消息、任务归属和终止检测的成本。

取消需要覆盖生命周期。先阻止未开始节点，再向运行中节点传播取消，区分“停止等待”和“远端已停止”。外部写入已经提交时，即使报告任务被取消，也要查询终态、登记操作 ID，按业务规则决定是否补偿。协议状态是调度线索，不能单凭 cancelled 字样断言远端没有副作用；受保护资源还要处理迟到请求。

收益评估看最终产物，不能把各分支得分相加。固定其余条件，去掉某分支或换成基线结果，观察质量、成本和延迟的变化。互评一致可能来自共享错误、相同资料或迎合评分规则，不能直接解释成独立支持，也不能由相同错误直接推断串谋。评分配置、文件与工具渠道要纳入控制，争议案例回到原始证据核对。

**常见追问：**

1. **取消后立即返还全部额度吗？** 不能。已提交调用可能继续计费，应保留待结算额度，确认用量或终态后释放剩余部分。
2. **换不同模型评审就独立了吗？** 未必。它们可能共享来源、偏差或候选诱导；需要和人工及客观验证结果比较。
3. **多 Agent 比单 Agent 成功率高就该采用吗？** 还要核对预算、尝试次数和验收标准。收益可能来自多花调用，需报告成功成本及退步任务。

**实战案例：**

教学案例三路研究中一路超时，一路存在版本冲突。用户此时取消，但上传 Worker 已提交请求。处理时停止新检索、通知其他 Worker，并沿原操作 ID 查询上传结果。验收应能看到取消后无新派发、已发生上传有对象记录、未知结果进入对账；单 Agent 对照表仍保留费用和最终质量，不以角色数量充当成果。

</details>

**常见误区：**

收到取消就删除所有状态；把互相给高分当作交叉验证；只报告成功案例的耗时，遗漏失败、重试和协调开销。

**微练习：**

为一条三分支任务画取消时序，分别在派发前、读取中、写入后取消。验收列出每个外部对象是否可能存在、哪些费用待结算，并给一个能检验分工收益的消融方案。
