# 15 · Text-to-SQL 与数据分析面试题

数据库肯执行，不代表数字回答了用户的问题。申请与明细的粒度、日期字段、可见范围和分母任一处选错，都可能生成格式漂亮、结果错误的统计。

配套 [学习章：Text-to-SQL 与数据分析](../../advanced/15-text-to-sql-and-data-analysis.md)，本章覆盖 Q099–Q101，练习先定口径、受控执行和独立核验。默认 [SQLite 实验](../../examples/sql_agent_lab/README.md) 使用预制候选，不宣称测出了自然语言模型效果。

### Q099 Text-to-SQL 怎样明确指标、映射 Schema，并避免 JOIN 放大？

**优先级：P0**

**30–60 秒回答：**

先确认对象范围、业务日期、状态、金额单位、数据粒度和分母，把问题写成指标卡；再将业务词映射到允许表列、枚举和关联键。申请表一行是一笔申请，连接多条明细会重复申请金额，应按所需指标直接聚合申请、用 EXISTS 筛选，或先把明细按申请 ID 聚合。SUM DISTINCT 按数值去重，无法替代申请身份去重。空值、撤销和日期选择要与口径一致。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

**Text-to-SQL** 将自然语言转换为 SQL，但业务任务还需要澄清、执行和解释。“10 月申请金额”至少要知道年份、业务日期字段、可见项目或租户、有效状态和金额单位；“超标比例”还要确认分母。若这些选择未定义，应返回待澄清项，而不是把默认值藏进生成结果。

**Schema linking** 把“申请金额”连到真实的 `applications.amount_cents`，把“申请日期”连到 `submitted_at`，并提供员工、申请和明细的关联键。列存在只证明结构可访问，不能证明它符合问题：`approved_at` 也存在，使用它会把申请窗口换成审批窗口。枚举、单位和时间字段的解释应与结构一起给出。

**粒度** 指一行代表哪个对象。一笔 650 元申请有两条明细，另一笔 700 元申请有一条，连接后申请金额会出现 650、650、700，SUM 得到 2000；原申请总和应为 1350。只需要申请总额时直接聚合申请表；明细只作存在条件时用 EXISTS；同时计算明细聚合时先按申请 ID 聚合，再检查连接键唯一性。

不能用 SUM DISTINCT 通用修复连接放大。它去掉相同金额值：如果两笔申请都为 650，正确总和为 1300，DISTINCT 却变为 650。应按业务对象身份保持粒度，而非寻找一个在当前样本上碰巧得到正确数值的语法。[SQLite 聚合函数](https://www.sqlite.org/lang_aggfunc.html)

NULL 和撤销会影响分母。配套合同只统计 submitted/approved；超标比例分母为金额和上限均已知的申请数，未知上限不计作未超标，另报总申请数与可比较数。这里的业务日期是规范化日期，没有执行时区转换；真实时间戳统计需先把业务区间映射到实际存储边界。

**常见追问：**

1. **金额总和用分还是元？** 示例用整数分存储并在展示时换算，避免把单位转换藏在候选里。不同币种还需要明确币种和换算时间，本实验没有实现汇率处理。
2. **没有明细的申请是否应被排除？** 要看指标。申请总额通常仍包含它；INNER JOIN 会意外漏掉它，因此应根据业务条件选择连接或存在筛选。
3. **查询返回零行就能说没有申请吗？** 只能说明当前数据快照、权限和条件下未找到。不能据此判断不可见数据或现实中不存在，也不能越权扩大范围寻找解释。

**实战案例：**

基线 fixture 两笔有效申请合计 1350 元，超标一笔，占可比较两笔的 50%。更换为两个 650、增加明细后，正确金额 1300，SUM DISTINCT 错为 650；第三份数据加入金额/上限未知项，申请数 3、可比较数 1、超标数 1。验收同时核对金额、计数、覆盖和分母，不只看一条 SQL 运行成功。

</details>

**常见误区：**

把真实存在的列当作正确业务字段；把连接后的行数当申请数；用金额 DISTINCT 替代主键去重；把未知上限归为未超标。

**微练习：**

手算 650/700 三条连接行的错误合计，再加入第三笔无明细申请。比较直接聚合、INNER JOIN、EXISTS 的对象集合。验收：能按指标选合适方法，并同时解释金额、申请数和缺失覆盖。

### Q100 模型生成的 SQL 怎样限制表列行、写操作和查询资源？

**优先级：P0**

**30–60 秒回答：**

候选 SQL 不能自己选择身份或高权限连接。宿主先根据可信身份限定可见数据，再限制允许表列、函数和操作，并设置语句大小、执行步骤、期限和返回量。参数绑定保护值输入，不自动约束任意 SQL 结构；只读也不等于租户隔离。SQLite 实验通过租户快照、authorizer 和 query_only 实施具体控制，不冒充 PostgreSQL RLS 或操作系统沙箱。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

执行控制从可信身份开始。用户输入、模型生成字段或自然语言中的“我是管理员”不能直接指定数据库作用域。宿主决定连接、权限和资源合同，候选只提供受约束的查询。参数化绑定日期和 ID 等值，不能因此允许任意表名、连接、函数或无界计算。

配套 SQLite 实验把 alice/bob 测试身份映射到租户，以固定参数化查询从只读源文件复制各自允许行，建立独立内存数据库。候选只能访问快照，不能拿到源连接，所以去掉 WHERE 也读不到另一个租户。源薪资字段不复制。该做法适合小数据实验，有复制与新鲜度代价；服务化时必须用真正认证替换测试映射。

**authorizer** 是 SQLite 编译期授权回调，检查读取表列、函数及操作。实验默认拒绝未允许的访问，即使语句以 WITH 开头，后面的 DELETE 也会被拒绝。候选不能读取内部表、附加别的数据库或加载扩展。只允许 SELECT/WITH 的前缀检查只是入口收窄，执行层回调才处理前缀掩盖的操作。[SQLite authorizer](https://www.sqlite.org/c3ref/set_authorizer.html)

`query_only=ON` 提供连接写入限制，但不会自动控制租户或脱敏列。多个层次应各自验证：行范围由可信快照承担，列/函数由授权回调承担，写入再由只读连接限制。不能把 SQLite 文件模式说成 PostgreSQL 角色或 RLS；数据库方言与实际运行角色不同，保证也不同。

资源层限制 SQL 文本、一个语句、返回行数及执行预算。进度回调按约 100 个 SQLite 虚拟机指令检查步数和期限，非零返回会中断；返回超过预算则报告超限，不将截断数据当完整统计。[进度回调](https://www.sqlite.org/c3ref/progress_handler.html) 这些不是精确 CPU/内存硬限额，也不能防御获得宿主代码执行权的人；生产需要进程与数据库层的额外隔离。

**常见追问：**

1. **只读 SQL 为什么还需要预算？** SELECT 可以产生巨大连接、递归或大量返回，仍会消耗资源。只读限制修改，不限制计算与数据量。
2. **越权失败能让模型修复到成功吗？** 应先确认用户有没有相应授权。不能把拒绝当作鼓励绕过的反馈；本实验遇到访问拒绝或资源超限就停止候选循环。
3. **加 LIMIT 是否就避免大扫描？** 不保证。聚合或排序可能先处理大量行再产生少量结果；需要执行预算和实际查询计划，返回行上限只约束结果量。

**实战案例：**

alice 候选移除租户过滤后仍只返回 a1/a2/a3，bob 只见 b1；读取快照禁用列、sqlite_master、加载扩展及 WITH 后 DELETE 被拒绝。递归 SUM 超过步数预算被中断，随后正常查询仍能执行。验收检查拒绝原因、返回对象集合和源数据库字节未改变，不只查看 HTTP 或进程成功码。

</details>

**常见误区：**

让模型传 user/tenant 选择高权限范围；认为参数化已约束任意 SQL；把只读等同隔离；只加结果 LIMIT 就称为计算资源限制。

**微练习：**

构造一条前缀为 WITH、实际执行 DELETE 的候选，以及一条返回很少但递归计算很多的 SELECT。验收：前者拒绝写，后者受预算中断，之后正常统计仍正确；分别指出哪层控制起作用。

### Q101 SQL 助手怎样有限修复，并用多数据实例核验语义？

**优先级：P0**

**30–60 秒回答：**

区分语法/字段错误、访问拒绝、资源超限和可执行但口径错误。可修复错误给出受控反馈，总尝试次数与预算预先限制；越权不能靠反复变形通过。业务语义由独立期望和多份数据实例核验，接受等价 SQL，不只比字符串或一次执行成功。策略不能提前读取隐藏标准答案；预制候选通过只证明执行与评分链路，真实模型能力要另设未泄题评测。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

数据库反馈能说明某个列不存在、语法不支持或执行被中断，但通常不知道用户真正想按申请日期还是审批日期统计。先按错误类别决定是否继续：语法、字段和部分方言错误可以尝试修复；访问拒绝需要停止或由用户合法调整授权；资源超限应缩小任务或结束，不无限放大预算。

有限修复需要总尝试数、期限和停止原因。配套实验最多两次候选，执行反馈逐次记录，不因异常重新启动就无界尝试。默认第一份编造列名、第二份使用正确列的轨迹是预制候选，用来检查反馈和上限，不证明语言模型学会修复。另一场景给五份错误候选，仍只执行两份。

**语义核验** 关注结果是否回答了指标合同。只比较 SQL 文本会误伤不同别名、谓词顺序或等价子查询；只看一份数据，又可能让错误查询恰好返回同值。多份实例改变重复金额、连接数量、缺失值和日期，能够暴露部分偶合错误。Distilled Test Suites 论文用一组数据库上的执行结果近似语义准确率；有限测试仍不提供任意等价证明。[论文摘要](https://arxiv.org/abs/2010.02840)

独立期望应在执行后参与评分，不能给生成或修复策略提前看。否则模型只需追逐已知金额，而不用理解查询。实验将三份 fixture 结果保存在独立 expected 文件，执行器和预制候选循环不读取它；测试另外验证等价改写接受、错误日期拒绝。评分通过范围仅覆盖明确数据与合同。

返回表还要连接到文字结论，说明金额单位、可见范围、日期依据、计数和分母。候选零行或金额未知时保留限制，不能生成“现实中不存在”或“全部未超标”。真实模型评测应固定模型/提示/Schema 版本，记录生成 SQL、修复次数、预算、执行结果和费用；本实验外部候选入口只执行文件中的 SQL，不核验其模型来源。

**常见追问：**

1. **标准 SQL 不同就一定错吗？** 不是。比较合同所需结果及允许的等价行为，并通过更多反例实例查错；不要要求字符串一致。
2. **评分器为什么可以看预期，修复策略却不可以？** 评分器是独立评估者。若隐藏答案进入策略观察，会泄漏任务结果，得到的成功率无法说明未见任务能力。
3. **一个错误 SQL 场景显示 passed 意味着什么？** 可能表示评分器按设计识别了错误。应读具体断言、候选结果和独立评分状态，不能把测试场景通过等同 SQL 业务通过。

**实战案例：**

按审批日期查询仍能运行，却把 11 月才审批的 a1 排除；独立预期发现金额和计数不匹配。SUM DISTINCT 在第一份数据碰巧修好 1350，两个 650 的第二份数据立刻失败；包含未知上限的第三份检验分母。验收保持隐藏预期与策略隔离，报告每份实例结果，不用总分掩盖失败类型。

</details>

**常见误区：**

把运行成功当业务成功；以字符串对齐代替语义；把隐藏金额放进修复提示；用预制 SQL 通过率宣传模型准确率。

**微练习：**

提交一份等价改写和一份错误日期 SQL 到 candidate 入口，比较三份数据的 grade。验收：等价实现通过，错误日期失败；另写一份未泄题指标任务，说明如何保留独立期望及真实模型成本记录。
