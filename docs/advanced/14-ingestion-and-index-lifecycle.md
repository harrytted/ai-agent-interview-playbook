# 14 · 知识摄取与索引生命周期面试题

把新文件丢进资料库，不代表新版条款已经替换旧索引；删掉原文，也不代表旧缓存失去了使用资格。摄取要交代“这是什么、从哪来、何时适用”，生命周期要继续证明变化影响了后续查询。

配套 [学习章：知识摄取与索引生命周期](../../advanced/14-ingestion-and-index-lifecycle.md)，本章覆盖 Q096–Q098。先读基础 RAG，再用 [真实词项索引实验](../../examples/knowledge_pipeline_lab/README.md) 观察身份、发布与访问边界。

### Q096 知识摄取怎样保留文档身份、来源位置和有效版本？

**优先级：P0**

**30–60 秒回答：**

分别保存稳定文档 ID、业务版本、稳定块 ID、内容哈希、源位置与适用条件。块身份说明哪条内容被修改，哈希说明内容是否变化，索引版本说明本次查询用了哪份完整数据。表格分块要保留表头、单位和行身份，不能只留下裸金额。查询按业务日期选有效版本，并核对当前访问资格；索引快照不等于同时实现了系统时间与业务时间的双时间模型。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

**知识摄取** 是从源资料到可查询派生数据的处理链，通常包括读取、解析、分块、元数据附加和索引。它首先需要回答“同一份文档如何识别”：文件名和存储路径会变，稳定文档 ID 则用于关联后续更新。业务版本区分制度或材料的正式版本，源内容哈希帮助检测变化，二者不可互换。

稳定块 ID 要尽量对应可解释单元，例如显式段落标识和表格条款行 ID。改金额时保持条款身份，改变内容哈希，才能追踪替代关系。如果把每次内容哈希直接当块身份，新旧对象之间还需要另外建立连接；如果按当前行号当身份，插入一段就可能让后面所有块改名。

解析会损失结构，必须在进入索引前检查。表格中的 700 需要与海岚、普通员工、元/晚和适用条件绑定。配套实验为每个表格行重复字段名，保存源 URI 和原始表头至该行的范围；这是简单 Markdown 表的保证，不是复杂 PDF 或 OCR 质量保证。**血缘** 指派生块到原文版本与位置的关系，后续删除和核验都依靠它。

从结构到块的诊断点是：解析得到的行是否仍知道所属表与表头，长段分割后是否保留父条款及原文范围，重叠块是否被误作独立证据。源哈希之外还要记录影响结果的转换配置；解析器或单位规则变了，旧缓存不能只因字节相同就复用。[分块与指纹机制](../../advanced/14-ingestion-and-index-lifecycle.md#从解析结构到块而不是先截一串字符)

业务有效时间决定政策何时适用，系统记录时间决定系统何时知道这个事实。实验以 `valid_from <= 出差日期 < valid_to` 选择同一文档的版本，并拒绝区间重叠；它保存 generation 快照，但没有“某系统时点所知事实”的查询合同，因此不能称作双时间数据库。资料若有追溯生效、例外规则或多层覆盖，需要单独定义冲突及权威顺序。

查询结果应带文档/块身份、版本、源位置、有效区间和索引 generation。这样可以把回答中的关键断言反查到具体材料，分清“解析错”“版本选错”和“生成误读”。来源定位存在也不证明该材料真的支持结论，仍需核对适用条件和原文含义。

**常见追问：**

1. **哈希相同是否说明文档可以直接复用？** 还要检查解析器版本和影响索引的元数据。权限、有效日期或解析规则改变，即使正文未变，也可能需要更新派生数据或访问目录。
2. **旧版资料应全部删除吗？** 不能一概而论。仍被授权的旧政策可以支持历史日期，撤回资料则要按当前使用资格失效；日期适用与访问资格是两个条件。
3. **扫描件提取出文本后，如何证明金额无误？** 需要与原图区域、表头和单位核对，保留提取置信与人工确认状态。预制 Markdown 只验证提取后的链路，不能替代 OCR 质量评测。

**实战案例：**

题设：同一检修手册的R8行写“扭矩20，单位N·m”，新解析器却把单位列丢了，正文原字节未变。文档身份和源哈希仍相同，不代表派生块合格；应改变处理规则指纹、重新生成并核对表头到R8的来源范围。若插入R7a导致行号变化，R8身份仍应稳定，位置则随新版本更新。这里考查身份、结构与缓存的不同职责，政策日期选版另由配套实验核对。

</details>

**常见误区：**

用上传时间代替生效时间；用文件名或当前行号作唯一稳定身份；保留金额却丢表头；把索引快照称为完整双时间查询。

**微练习：**

给一份两版本政策设计源清单，并为表格两行标稳定条款 ID。新增一行、修改一行金额后预测哪些身份和哈希应变化，再运行实验接口核对。验收：两次业务日期选择正确，修改条款身份不漂移，金额和单位可追溯到源位置。

### Q097 增量摄取怎样处理中断重跑，并避免半成品进入查询？

**优先级：P0**

**30–60 秒回答：**

用源内容、元数据和处理规则的指纹识别变化，复用未变对象；变化对象写进可恢复暂存区。先完成并验证候选索引，再切换可见指针，读者不能看到未完成的新索引。重跑按源指纹使用已暂存对象，保证重复处理不制造重复业务块。配套实现是本地单写者的增量解析加完整倒排重建，没有因此获得并发发布或跨机器事务保证。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

**增量处理** 是根据变化范围减少重复工作，不是给目录追加一批新块就结束。需要稳定源身份、内容指纹和处理规则版本，判断同一源是否改变。元数据会影响版本筛选和访问，不能只比较正文。重复提交同一完整清单应复用已有对象，并保持块数量与查询结果稳定。

中断发生在读取、解析、分块或索引写入之间时，应知道哪些步骤已完成，哪些还未公开。配套实验把已解析对象、指纹写入持久 staging；用新 `Pipeline` 实例重跑时，从磁盘识别可复用对象。若源内容又改变，旧暂存指纹不匹配，不能直接发布上次半成品。

**发布点** 是读者开始看到新版本的明确边界。实验先写一份包含文档清单、块与完整倒排表的 generation，校验后再原子替换 state。读者先取一次 state，之后只读其指定索引。处理中断时 state 保留旧 generation，因此新金额即使已经存在 staging，也不会提前进入查询。

这份实现只重新解析变动源，但会重新构建完整倒排表。它在教学数据下容易检查，不声称达到大数据量的 posting 原地更新效率。真正的增量向量或图索引还要处理删除、实体合并、摘要传播和更新原子性，变化成本可能远大于源文件数量。

单写者假设也必须公开。同一文件系统上的原子替换并不自动防止两个写者互相覆盖，进程中断验证也不等于断电和跨机器故障验证。若要多个摄取 worker 并发，可以让它们处理独立对象，但最终提交仍需互斥、比较版本或事务协议，并用相应故障重放证明。

读者固定generation后，还要保留它所需的文件。发布g2后立即删除g1，可能使正在读g1的查询失败；读者中途重读active，又可能混用g1块与g2倒排表。应分别设计发布、读者固定和旧文件回收，不能用一次指针替换替代全部生命周期。[发布与回收条件](../../advanced/14-ingestion-and-index-lifecycle.md#指针为何能提供整批可见性)

**常见追问：**

1. **为什么不边处理边公开新块？** 可以设计逐对象一致性合同，但用户可能同时读到新旧版本的混合。若承诺整批一致，就应在完整候选验证后发布，不能只为了可见进度提前切指针。
2. **重复摄取如何区别于真正的新版本？** 比较稳定源身份与处理指纹；同内容同元数据同规则可以复用，业务新版本则单独记录。不能用“文件每次下载路径不同”制造无限新对象。
3. **原子替换是否已经足够部署到对象存储？** 没有。对象存储的条件写、一致性和多对象可见性需要按实际服务合同设计，不能把本地文件 API 保证直接移植过去。

**实战案例：**

三份政策中两份发生变化。管线暂存第一份后被注入中断，用户仍查询到旧金额 700。新实例重跑复用一份 staging、继续处理剩余变化，发布完成才返回 730。验收同时检查旧指针、暂存日志、复用计数和实际查询，不只检查重跑进程退出 0。

</details>

**常见误区：**

只增不删；把每次重跑当新文档；尚未建完索引就宣布新版可见；把本地单写者恢复结果包装成分布式高可用能力。

**微练习：**

先运行 `interruption`核对暂存与发布。再分析时间线：读者R固定g1→写者发布g2→清理器删除g1→R读取第二份文件失败。指出中断重跑测试为何没有覆盖此问题，并给出读者引用或保留期的回收条件。另将块词项从`alpha beta`改成`alpha delta`，列出必须移除与新增的posting；只增加delta却保留beta不是正确增量更新。

### Q098 删除、撤权和索引回退怎样避免旧内容再次被使用？

**优先级：P0**

**30–60 秒回答：**

沿来源血缘处理原块、派生索引和缓存，并把当前使用资格作为查询与上下文组装的独立条件。旧索引快照只能提供历史内容，不能恢复已经撤回的权限或已删除资料。回退数据索引时保留当前访问目录，检查旧 pinned generation 与正常查询都受限制。配套实验验证新查询过滤，没有清除已返回文本、磁盘旧文件或外部模型上下文；真实服务要另外处理这些边界。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

删除和撤权改变的是当前可使用集合。原文件消失之后，向量、词项块、图关系、摘要和答案缓存仍可能携带内容，所以首先需要来源血缘列出受影响对象。图派生更新往往还会重建相关实体关系，不能假设只删一份原文就完成。[LightRAG](https://github.com/HKUDS/LightRAG) 可作为更复杂派生维护的选读实现。

配套实验通过最新 catalog 表示当前存在的文档版本及 principal 权限。新完整清单中未列出的版本不再可查询，撤回 principal 后该身份不再有读取资格。词项索引提供候选，当前 catalog 决定候选能否进入结果；即使调用者指定旧 generation，也要经过当前目录。

**索引回退** 为了恢复一份可读的完整索引，不应同时恢复过期权限。实验的 `activate` 只改索引指针，保留当前 catalog。于是旧 generation 中虽然还保存着 v2 文本，删除 v2 后也不能重新返回；撤回 employee 后回退，admin 能读而 employee 仍不能读。

需要明确控制输入的权威来源。实验单写者将新完整清单视为可信授权更新，管理员再次提交允许 employee 的清单时会重新授权。若真实系统要防止旧资料清单覆盖新撤权，应把权限版本、来源新鲜度与授予规则分开管理；“回退不恢复权限”不是对任意后续重新授权操作的永久否决。

缓存与在途任务是另一层。已经返回的文本不会被远程收回，已进入模型历史的材料可能需要清理或阻止继续输出。生产系统应定义撤权何时生效，在查询、上下文组装和结果返回处核对必要资格，并记录不能清除的已披露范围。本地实验无外部缓存或模型会话，因此不能声称已验证端到端撤权。

删除的依赖范围可沿`源→块→摘要/缓存`找受影响子图。多源摘要的一条依赖被撤回，不能只删该关系而继续返回原摘要；要重建或使其不可用。目录阻断、派生失效、物理清除应各有完成记录；墓碑只有在全部读取路径都核对时，才阻止旧副本继续使用。[删除层次](../../advanced/14-ingestion-and-index-lifecycle.md#删除撤权和回退必须一起验证)

[16章服务实验](../../examples/service_lab/README.md)进一步检查任务返回层：内容release固定，当前文档目录以access_revision独立变化，GET旧答案和待批草稿也重新核对。它尚未连接本章Pipeline；两个实验分别验证索引查询与任务视图，不能把其中一处过滤当整条链路已经安全。

**常见追问：**

1. **保留旧 generation 是否违反删除？** 取决于删除合同。实验验证查询不可见，旧磁盘文件仍用于审计与回退；需要物理清除或保留期管理时要另行实现，不能把逻辑过滤等同安全擦除。
2. **如果撤权后又收到旧的允许清单呢？** 必须比较权限版本或可信事件顺序，不能让陈旧资料覆盖新授权状态。本实验只支持可信单写者顺序操作，未实现外部权限事件仲裁。
3. **新 Embedding 模型上线后能随时回退吗？** 还要保证旧读取器、向量维度、距离规则和数据仍兼容，且当前权限目录持续适用。参数维度相同也不表示两套模型向量可混用。

**实战案例：**

先发布 700 元版，再更正为 720 元，随后撤回 employee。正常查询和指定旧 generation 都返回空；切回 700 元 generation 后，employee 仍空、admin 可读。删除 v2 的场景还保留 v1，因此历史日期有合法来源，新日期不凭旧文件补猜。验收检查当前目录修订号、查询结果和回退记录。

</details>

**常见误区：**

只隐藏源链接；认为召回后不展示就不会进模型上下文；把索引和权限一起回退；仅凭逻辑删除测试通过，就声称已经擦除所有副本。

**微练习：**

发布两个 generation，撤回一个身份后指定旧 generation 查询，再回退。验收：旧索引不绕过当前访问目录；另写出外部答案缓存、已生成上下文和磁盘留存各需要什么额外处理，区分已实现与设计项。
