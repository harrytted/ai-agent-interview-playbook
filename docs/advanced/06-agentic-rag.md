### Q072 Agentic RAG 怎样围绕证据依赖选择检索路径？

**优先级：P0**

**30–60 秒回答：**

先把结论拆成必要证据和依赖，再决定查文档、SQL 还是业务工具。上一步返回的项目 ID 若是下一步查询条件，就存在真实多跳依赖。自适应策略可选择不检索、单次或迭代，但不能只看问题长短，还要看时效、权限和证据风险。每次查询应补具体缺口，而不是不断换词搜索。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

从用户结论反推最小证据集。例如判断项目例外审批是否增加，需要项目范围、两个可比窗口、例外数及分母；讨论与政策的关系，还需要适用制度、人员类别与生效区间。将这些节点写成输入输出合同，连接真实数据依赖。项目目录先返回允许访问的 ID，统计查询才能确定范围；先并发搜索一批名字不等于多跳推理，缺少连接键仍可能把不同项目混在一起。

按信息形态选路径。正式条款用文本检索，精确数量用受控 SQL 聚合，归属关系可用业务 API。统计必须保留日期字段、去重、撤销过滤、分母和数据时间。SQL 参数化保护值输入，不自动限制任意表名、连接或资源消耗；还需限制表列行及执行角色。PostgreSQL 行级策略也要核对所有者、超级用户和 BYPASSRLS 等绕过条件，不能让高权限共用账号破坏租户隔离。

自适应检索在成本与证据要求之间选择策略。Adaptive-RAG 研究用查询复杂度分类来选择不同检索开销，但企业问题还取决于当前信息与访问条件。短短一句“今天生效了吗”可能需要跨版本核对，材料充分的固定问题也不必机械迭代。零行应区分范围内无数据、权限过滤、同步延迟和错误参数；关键映射无法取得时保留不可比状态，避免用生成补齐。路径更灵活也更难排障，因此每次决定都要关联到尚未解决的节点。

**常见追问：**

1. **所有来源都向量化不就统一了吗？** 会损失精确统计和结构约束。数量、连接与过滤宜保留结构化查询，文档检索负责条文与解释，最后按稳定键连接证据。
2. **哪些节点能并发？** 输入已确定且互不依赖的节点可以并发；必须等项目 ID、人员映射或制度版本才能确定的查询应等待依赖，不能靠猜测提前执行。
3. **查询失败后怎样重规划？** 先识别缺哪个证据及失败原因，选择有权限的替代来源或报告缺口。反复改写相同问题不会自动解决权限、映射缺失或统计合同错误。

**实战案例：**

研究三个项目的例外变化，A 的例外数从 10 增至 20，总数从 100 增至 400；B 中途换承包方，人员映射缺失。助手先取项目目录，再查数量，计算 A 占比从 10% 降至 5%，补查适用政策与 B 映射。验收要求 A 的计数与比例分开报告，B 暂不进入无条件排名，每条结论标明数据时间和条款；即使两者变化与政策时间相邻，也不输出已证明因果关系的结论。

</details>

**常见误区：**

把长问题等同复杂、短问题等同简单；把并发搜索当多跳；认为 schema 或参数化通过就保证 SQL 查询范围与统计正确。

**微练习：**

为该研究画证据 DAG，标来源、前置条件和失败状态。验收：能够指出哪些节点可并发，正确复算 A 的比例，并明确 B 缺哪个映射、为什么不能靠文本检索补猜。

### Q073 GraphRAG 的局部与全局查询怎样选择和维护？

**优先级：P1**

**30–60 秒回答：**

GraphRAG 在入库时抽取实体和关系、构建社区并生成摘要，提前支付理解与组织成本。Microsoft GraphRAG 的局部查询结合具体实体周边图信息与原文，全局查询汇总社区报告，适合不同问题范围。图和摘要是派生索引，更新与权限必须贯穿血缘，集合摘要不能直接证明某笔申请符合具体规则。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

先判断关系结构是否真的有用。项目、供应商、人员和地区反复关联时，实体解析与关系索引可以帮助回答某项目关联哪些组织或哪些风险跨项目出现。Microsoft GraphRAG 的标准索引流水线包含抽取、社区构建、报告和嵌入等工作，它们把一部分查询时理解搬到入库阶段。抽取错误和同名实体合并错误也会进入图，因此每个派生节点都应能回到原始材料及版本。

查询方式按范围选择。局部查询围绕具体实体组织图信息与原文片段，适合追查项目关联条款；全局查询对社区报告进行 map-reduce，适合资料集合的共同主题。全局汇总不能取代单个对象的适用规则核验，局部邻域也不保证覆盖集合全貌。若问题只是明确条款检索，普通检索可能更直接；不能因为图结构复杂就假定答案更可靠，需要在相同任务与预算下比较。

维护与访问是主要工程代价。文档更新可能影响原块、关系、实体归并、社区报告和缓存，甚至改变更广的聚合结构，因此用来源血缘定位并重算，不能按“只改一篇”假定只更新一个节点。摘要若混入两个可见域，底层检索再过滤也无法消除摘要已携带的内容。应按可见范围构建或生成派生数据，并在使用时保持隔离与新鲜度合同。预计算能加快某些查询，却带来更新延迟、资源消耗和授权管理成本，应明确允许的陈旧窗口与失败行为。

**常见追问：**

1. **知识图谱是不是比文本更权威？** 不是。图关系和社区摘要由抽取与生成得到，必须保存来源，并核对实体、时间和条件，不能把派生索引升级成新的事实来源。
2. **一份政策撤回后删原文就够吗？** 不够。关系、报告、向量候选和缓存可能仍传播旧内容，要沿血缘失效并重算受影响范围，新请求不应继续使用旧派生结论。
3. **能否只给最终摘要做 ACL？** 若摘要已经混合不同租户或权限材料，简单挂一个通用权限标签可能泄露内容。需从构建、生成到使用明确可见范围，不能靠链接隐藏修复。

**实战案例：**

企业研究库包含多个项目与供应商，团队想比较共性风险并检查一笔住宿申请。先用全局报告找候选主题，再对该申请使用局部关系和适用原条款。随后一份政策撤回，且一篇社区摘要混入受限供应商材料。处理时按血缘停止返回受影响报告，重算并拆分可见域。验收确认共性主题能回查来源、单笔判断有具体条文，普通员工不能从摘要读到受限内容，撤回政策也不残留在新答案中。

</details>

**常见误区：**

把图当真相数据库；把全局总结当单对象证明；只算查询成本，不算抽取、消歧、更新和权限分区成本。

**微练习：**

给三个问题选择普通检索、局部或全局查询，并画派生血缘。验收：能解释每种选择的证据范围，撤回一份原文后列出需失效对象及重新可用条件。

### Q074 研究助手怎样反向核验证据并决定停止？

**优先级：P0**

**30–60 秒回答：**

从草稿关键断言反向找支持它的证据，核对原文含义、版本、适用条件、数值和相反材料。为调用数、时间、token 和来源范围设置预算，每次新增查询必须对应缺口；证据完成或无法继续都可以停止，后者返回部分结果和未决项。排障要区分分解、路由、召回、连接、统计与生成，不能统一靠增大 top-k 修复。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

正向检索结束后，先把草稿拆成可检查断言，再逐条反查来源。检查链接指向的内容是否真的支持该事实、版本与人员日期是否适用、数值能否由原始查询复算，以及是否存在未解释的反证。链接可打开只证明定位成功，不能证明蕴含关系。模型可以辅助语义核对，确定性计算与对象状态应由程序或业务服务确认；材料未覆盖的部分明确标为推断或未决，避免引用装饰。

停止合同在任务开始就约定。必要节点已有充分支持时结束；关键来源不可访问、连续查询没有新增有效信息、总期限或调用预算耗尽时也应结束，但只返回已支持部分与缺口。示例总预算为 8 次外部查询，不给每个分支各发 8 次；发起前统一预留，记录这一调用试图解决哪个问题。预算控制的是资源，不能把最后一次失败结果改写成确定答案以满足“必须完成”。

错误归因沿流水线展开：分解是否漏节点，路由是否选错来源，召回是否遗漏，材料是否失效或越权，连接键和统计口径是否正确，最后才看生成误读。可以用人工正确证据替换召回结果检查后半程，也可固定结果重新复算统计。若错误在 SQL 分母，增大文档 top-k 不会解决。更严格核验增加时延与成本，因此优先覆盖决定结论的断言，保留核验状态和未覆盖范围，不能用一个总置信度抹平差别。

**常见追问：**

1. **证据不足为何不一直检索？** 部分缺口来自无权限、未入库或无法比较，继续改词只消耗预算。应识别可改变条件的下一步，无法推进则清楚结束并报告缺失依据。
2. **怎样区分检索错还是生成错？** 提供人工确认的正确材料并保持问题与评价合同不变。若仍误读，检查后续推理与输出；若改善，再追查召回、过滤和版本链路。
3. **有两份支持材料就能下因果结论吗？** 数量不替代研究设计。趋势与政策时间相邻通常只支持关联线索，需要更强证据和方法解释混杂，不能靠多放引用升级结论。

**实战案例：**

助手根据计数上升写出“新政策导致例外比例增加”。反向检查发现 A 的例外占比实际上从 10% 降至 5%，B 的人员映射缺失，C 只找到过期通知。处理时复算 A，剔除 B 的无条件比较，给 C 分配版本补查；第 8 次调用结束后保留 C 的未决项。验收检查每个关键断言的证据映射、调用账本和停止原因，确认错误定位在分母、映射和版本，而不是笼统归为模型幻觉。

</details>

**常见误区：**

用引用数量代替支持强度；把预算耗尽当必须猜完；把所有失败归因于召回不足，或把相关变化写成已证明的因果关系。

**微练习：**

为五条草稿断言建立证据核对表，并分配 8 次查询预算。验收：每次调用有对应缺口，数值可复算，关键来源不可得时输出局部结论和具体未决原因。
