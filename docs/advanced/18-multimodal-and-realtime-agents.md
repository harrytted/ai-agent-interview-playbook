# 18 · 多模态与实时交互面试题

对应学习章：[18 · 多模态与实时交互](../../advanced/18-multimodal-and-realtime-agents.md)。Q108属于18A媒体证据基础；Q109–Q110进入18B实时播放和语音链路选修。原始媒体、识别候选、用户确认、播放进度和业务终态分别保存。

### Q108 图片区域、页码与语音片段怎样对应到可核验的事实？

**优先级：P0**

**30–60 秒回答：**

每项观察关联原始媒体ID与版本，图像记页码、画布尺寸和区域坐标，音频记开始结束时间、说话者及转写阶段。保留原始内容、识别候选、用户确认和最终结论，位置合法不等于识别正确。临时转写不能直接成为已确认业务条件；票据650与转写6500冲突时应澄清。用户更正后递增条件版本，查询和结果绑定该版本，旧城市结果不能支撑新城市结论。固定夹具能检验关联和状态，不能证明OCR、ASR或视觉识别质量。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

**媒体证据定位**是把一项观察指回可检查的原始对象。图像应有媒体标识、版本、页码、画布尺寸与坐标单位，音频应有文件标识、时间范围和转写阶段。只保存“识别金额650”会丢失复核入口；只保存文件名却没有区域或时间，也难以定位误识别发生在哪段内容。

本地自绘票据为640×360，金额框是`[80,180,460,70]`。程序检查x、y非负，宽高大于0，区域不超过画布；音频时间检查`0 <= start < end <= duration`。若预处理做了缩放、裁剪、旋转或重采样，应保留与原媒体之间的转换关系。检测框坐标在图内只说明位置格式合理，不能证明它框到了金额，更不能证明数字读对。

**OCR**提取图像文字，**ASR**识别音频文字，**多模态模型**也可能直接解释图像和音频；这些输出都是需要核验的候选。保存候选、置信或不确定标记和人工确认，比把识别文字立即写为真值更稳妥。来源含糊、票据不清或跨模态冲突时，应先请求澄清，避免用流畅总结掩盖650与6500的差异。

**临时转写**在识别过程中可能变化，**最终转写**只表示当前识别段完成，不保证事实无误或用户不会更正。实验只让最终条件改变业务状态；每次有效变化递增`condition_version`并使旧政策结论失效。工具调用保存条件版本和城市，回包同时检查调用ID、版本与城市。这样，即使海岚查询较慢，在用户改为云洲后也不会污染新结论。

本实验的票据与提示音是原创素材，金额观察与转写是人工构造夹具。提示音没有说出转写文字，时间片仅用于练习关联；程序通过不能被当作语音识别正确。真实接入应保存原媒体、模型/协议版本、识别输出、人工核对及最终业务结果，分别统计识别与推理问题。

**常见追问：**

1. **模型给了很高置信度，还需要来源位置吗？** 需要。置信度不是可回查证据，也可能未校准；位置帮助人工复核和定位错误，但仍要核对内容。
2. **final转写之后用户改城市，是否属于新任务？** 取决于任务合同，但至少要创建新的条件版本并使旧依赖失效；不能继续沿用旧城市的制度结论。
3. **旧工具返回要从日志删除吗？** 不必。可保留用于审计和排障，但标注它绑定旧条件，不能进入当前结论的支持证据。

**实战案例：**

票据金额650，临时转写6500，系统暂不修改确认金额；最终转写650后发起海岚查询。用户更正云洲，条件版本从1到2，海岚回包随后到达。正确流程记录一个旧结果，查询云洲并使用其650元上限，因此当前650元草稿判断不超标。若最终转写仍为6500，则先进入`needs_confirmation`，即便查到了政策也不生成确定草稿。

</details>

**常见误区：**

图片已上传等于视觉已识别；坐标合法等于内容正确；final等于永不可改；抹掉旧结果代替版本隔离；把固定转写运行通过称为ASR效果好。

**微练习：**

运行`python3 examples/multimodal_lab/lab.py --scenario correction`与`uncertain`，核对最终城市、旧结果计数和草稿。再把金额框改为越界坐标，解释定位错误和内容错误分别在哪层被发现，并说明还需要什么证据才能测识别准确率。

### Q109 用户打断后，生成、播放、历史和在途工具怎样保持一致？

**优先级：P1**

**30–60 秒回答：**

分别跟踪已生成、待播放和实际播放，用户打断时停止当前播放器，取消不应继续的输出，并将历史限制到已播放范围。每次输出有generation标识，旧代次迟到音频或进度不能继续扩充历史。浏览器currentTime只是媒体时钟，不证明用户实际听见；真实文本裁剪还需要词句对齐。工具结果绑定条件版本，更正后迟到结果只能留审计；受保护动作若已经提交，打断不等于撤销，应查询业务终态。暂停可继续，打断取消当前输出，两者应有不同状态。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

**打断（barge-in）**发生在助手输出过程中用户希望取得话语权时。运行时至少有生成进度、客户端缓冲、播放进度、会话历史和工具执行五个对象；若只在服务端设置停止标记，已经缓冲的音频还可能继续播放，历史也可能记录用户从未听到的内容。

可以为每次输出分配**generation（输出代次）**，音频块和进度事件都关联该代次。会话保留已见代次与取消记录，不能用同一个生成ID重新初始化来清掉历史；新输出必须换新ID。先判定事件是否属于当前有效代次，再检查该代次的时长与位置。例如旧g1长4秒、新g2长2秒，g1迟到的3.8秒进度应直接忽略，不能套g2时长报错或扩充g2历史。打断时先停止播放，记录当前可核实媒体位置，再取消当前生成路径或向供应商发出协议支持的取消请求；之后丢弃该代次的迟到块。是否真的远程取消成功需要供应商回执或相应协议证据，不能从本地静音直接推断。

已生成4秒不等于已播放4秒。浏览器在1.25秒打断，本地演示保存历史媒体范围0到1.25秒，拒绝旧代次后续3.8秒进度。真实语音系统若要裁剪对话文本，还需知道哪些词句对应这个音频位置，处理部分单词、TTS缓冲和播放回执。`currentTime`可以读取媒体时钟，但不能证明用户耳机有声、实际听到或理解了内容。

暂停与打断也不同。暂停暂时停止同一代次，继续时可接着播放；打断意味着当前输出被取消，下一次输出应进入新代次或明确的新轮次。UI应展示区别，不能一边显示“已取消”一边又允许旧缓存自动继续。LiveKit提供自动打断与历史裁剪行为，但接入时仍需核对所用SDK和实时模型的轮次配置。

在途工具另按任务语义处理。用户把海岚更正为云洲后，海岚只读查询可保留但不能支持新结论；未开始的受保护写入可以取消。若工单创建已远程提交而本地确认丢失，应沿原业务意图查询真实对象，打断不会使外部动作倒流。会话轮次结束、任务结束和业务副作用结束是不同状态。

**常见追问：**

1. **停止服务端生成是否足够？** 不够。还要停止或清理客户端待播缓冲，处理迟到块，并使历史与可核实播放范围一致。
2. **把打断时的currentTime写进日志就完成文本裁剪了吗？** 没有。它只提供媒体位置；文字历史裁剪还需字词或句段与音频时间的对齐。
3. **用户打断就取消所有工具吗？** 不应一刀切。更正使旧读结果失效，但已提交动作要核对终态；是否取消、继续或等待用户由任务和授权合同决定。

**实战案例：**

助手生成了4秒回答，本地播放器播放到1.25秒时用户点击打断。错误实现只停止生成，播放器仍播完缓存，日志却写“用户取消”。本实验将代次标记取消、暂停实际音频、记录历史范围，旧进度被计为忽略；继续按钮拒绝重播旧代次，重置后才能开始新代次。离线场景进一步注入3.8秒的迟到进度，验收历史仍为1.25秒，而不是只检查取消事件出现过。

</details>

**常见误区：**

生成时长等于听到时长；本地暂停等于远程取消成功；丢弃旧音频却继续保留整段历史；打断当成业务撤销；不区分暂停、取消与新轮次。

**微练习：**

打开[真实播放演示](../../examples/multimodal_lab/player.html)，播放后先暂停再继续，然后中途打断。下载日志，核对播放位置、打断历史上限和取消后拒绝继续；另运行`interruption`场景，解释浏览器实播证据与离线迟到事件注入分别证明什么。

### Q110 怎样比较两类语音架构，并设计专项评测？

**优先级：P1**

**30–60 秒回答：**

级联ASR—语言模型—TTS便于分段观测和修复，但会叠加等待；原生实时音频会话可以减少部分阶段切换，却仍需轮次、工具、打断和历史合同。先固定语言、任务、噪声、网络和预算，再分别评测识别、轮次检测、首音延迟、误打断、工具与任务结果。平均延迟不够，要记录分布、失败和测量边界。固定JSONL只能验证状态，提示音实播只验证播放器；它们都不能替代真实语音识别、自然度、实时模型或网络评测。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

**级联语音链路**把ASR识别、语言模型决策与TTS合成拆成可观察阶段。可以逐段检查文字、改转写、替换供应商，也能看到哪一段造成650变6500；代价包括阶段等待、文本瓶颈和额外状态交接。**原生实时链路**在实时会话中处理音频输入输出，可能保留更多语音信息并减少部分转换，但是否满足任务质量和时延仍需实际测量。

轮次是两类架构共同的约束。**VAD**判断语音活动，不能独自证明一句话结束；用户思考时停顿、“嗯”的附和、噪声和真正打断应区分。服务端实时模型可能自己管理轮次，框架也可能通过VAD和语义模型管理，两边重复启用不一定得到更好结果。应固定实际SDK配置并记录由谁决定结束、谁发起取消。

评测先建任务集合，而不是先选一个漂亮时延数字。媒体层覆盖中文数字、日期、城市、票据清晰度、口音和背景噪声；交互层覆盖临时转写、纠正、长停顿、误打断与真正打断；工具层覆盖延迟、失败、旧条件结果；业务层核对最终城市、金额、来源与是否产生正确对象。保持失败样本，避免只测能顺利读完的一段话。

时间指标要说明起止。首音延迟可以从用户轮次结束到客户端开始播放首个音频，不能拿模型首次生成字节冒充；打断响应可从真实打断信号到停止播放，需记录检测和播放器两端事件。报告中位数和尾部表现时同时写样本数、网络条件、模型/SDK版本与失败数，不能将超时样本直接删除后宣布更快。自然度与可懂度需要真人或经过校准的评价，正确播放不等于好听。

本仓库默认实现离线JSONL状态机和真实提示音播放器，没有ASR、TTS或实时模型。它们适合先验证协议与状态，再按可选接口增加真实评测。比较架构时，可保持相同业务任务和预算，分别记录识别错误、推理错误、控制错误与费用；不要用一种架构额外多次重试后的最好结果对比另一种首次结果。

**常见追问：**

1. **端到端实时模型一定比级联更快吗？** 不能预设。模型、网络、轮次检测、工具等待和客户端缓冲都会影响实际播放；应在同一任务与测量边界下比较。
2. **识别字错率低，任务就一定好吗？** 不一定。城市或金额等关键字段的一次错误可能改变结论；还需关键实体、工具参数和最终业务结果评测。
3. **为什么不能用合成提示音验证ASR？** 提示音没有语音内容，也没有可核对转写。它能验证文件加载、时长与播放控制，不能提供识别质量的分母。

**实战案例：**

团队比较两种差旅助手，只记录模型返回首字节，实时方案看起来更快。但实际播放器等候缓冲，用户说“是云洲”时又被当成附和，结果仍用海岚政策。重新评测时记录用户轮次结束、模型输出、首音播放和停止播放，加入城市更正、650/6500与旧查询迟到。按任务核对最终结论，并把真实模型结果与本地状态自检分开，才能看出速度提升是否牺牲正确性。

</details>

**常见误区：**

只测平均首字节；删除超时样本；VAD等于轮次理解；实时接口免除工具状态管理；提示音和人工转写构成语音识别基准；英语表现直接代表中文表现。

**微练习：**

为同一差旅任务设计6类样本：正常、数字冲突、城市更正、长停顿、误打断、工具迟到。每类写明输入、预期终态、时间起止和证据层级；标出当前离线实验能测哪些，真实接口和真人听测还需补哪些。
