# 02 · 持久执行面试题

工单已经创建，成功响应却没回来，恢复后该再点一次吗？重试要拿着原收据查结果，不能一着急就重新下单。持久执行要说清恢复计算、批准动作和外部事实各由谁负责。

配套 [学习章：持久执行](../../advanced/02-durable-execution.md)，本章覆盖 Q060–Q062，围绕重放窗口、审批与并发接管展开。

### Q060 持久执行为什么仍需要外部幂等？

**优先级：P0**

**30–60 秒回答：**

持久执行恢复的是记录与计算边界，跨服务的写入仍可能处于结果未知。更复杂的情况是旧尝试的成功回包迟到，同时恢复流程正在查询。两条证据都必须归并到原业务操作 ID，核对参数与对象，不能分别创建第二个意图。幂等和结果确认由外部合同共同支持。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

固定案例：本地已保存 op17 与650元草稿；尝试 a1 在远端创建 ticket9，调用方超时。恢复发出 lookup(op17)，此时 a1 的迟到回包也返回 ticket9。这里需要处理的是证据归并，不是再创建一个“恢复工单”。

| 到达信息 | 归并动作 | 禁止动作 |
| --- | --- | --- |
| 旧尝试返回ticket9 | 核对op17、对象与原参数，登记来源a1 | 用旧尝试覆盖新业务条件 |
| 恢复查询返回ticket9 | 对同一对象确认一次，保留两份尝试证据 | 创建新operation_id来“修复”本地状态 |
| 两条信息对象不同或参数不同 | 保留冲突并接管核对 | 随便选较晚回包宣布成功 |

本地确认应具有幂等语义，已确认同一对象时重复登记不会产生第二份业务动作。业务意图、尝试和对象分开保存。若期间用户将金额改成800元，旧650元对象仍是已发生事实，应报告该事实并处理新请求的批准，不能抹去原对象或让旧批准覆盖新内容。

外部合同必须说明同 ID 相同参数、不同参数、保留期与查询可见性。并发接管还需所有权或 fencing 等控制，具体讨论留到Q062；本题先证明迟到响应和恢复查询没有分裂成两个意图。

**常见追问：**

1. **迟到回包来自旧进程就应丢弃吗？** 它可能证明真实副作用，先归并核对，不能因进程旧就抹掉业务事实。
2. **两次确认同一对象需要再次创建吗？** 不需要；本地确认应可重复，外部对象保持一份。
3. **用户更改条件能否复用旧批准？** 不能。原结果需核对，新内容重新匹配批准。

**实战案例：**

本仓库T12实际覆盖“远端提交后、本地未确认”的两进程恢复。上表的迟到回包并发属于额外设计题，并未宣称离线实验模拟了真实网络并发。答题时分别说明已跑出的证据与设计推演。

</details>

**常见误区：** 把重试当新业务意图；忽略迟到回包；用最后到达时间代替对象与参数核对。

**微练习：**

写一个含operation_id、attempt_id、object_id、payload_hash的归并表。合格答案让两次同对象确认收敛；较好答案保留冲突与已发生事实。新条件：查询暂未找到而旧回包已证明创建，应先核对服务合同，不能自动换ID重建。

### Q061 怎样让审批与 Outbox 在恢复后仍保持正确含义？

**优先级：P0**

**30–60 秒回答：**

审批应绑定具体动作版本，包括对象、工具版本、规范化参数、收件人和附件，并独立验证审批人身份与权限。批准后把业务状态和待发送事件写进同一本地事务，再由分发器投递。Outbox 解决本地双写窗口，投递仍可能重复，下游需要幂等。旧批准不能无条件覆盖修改后的报告。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

审批先需要一个可恢复的业务对象，而不只是布尔值。保存请求 ID、申请人、报告版本、动作摘要、参数 hash、有效期和当前状态。摘要应覆盖真正会执行的动作，例如发布到哪个对象、由哪个版本的工具执行、发送哪些附件。Hash 只是绑定内容的方式，不证明谁批准，也不能代替审批人当前权限检查；动作变化后按业务合同重新建立批准关系。

等待阶段将 pending 状态持久化并释放执行资源，恢复收到外部输入后，重新核对请求是否已失效或被新版本替代。Interrupt 提供暂停与恢复机制，权限、过期和版本匹配仍由业务实现。重放还受代码顺序影响，不能随意调整旧运行中的 interrupt 和任务位置；应固定版本或在兼容路径上迁移，避免把一次输入匹配给另一个动作。

批准后若需要同时记录“已排队”和发送事件，可以把业务状态与 outbox 行放入同一数据库事务，提交后再投递。事务未提交，两者都不生效；提交后分发器继续处理。但远端收到消息和本地标记已投递之间仍有窗口，所以事件 ID 必须稳定，消费方按合同去重。这里换取的是明确的本地一致性与可恢复投递，代价是后台分发、积压监控和对账，并没有获得跨系统一次性执行承诺。

**常见追问：**

1. **只对正文做 hash 可以吗？** 若收件人、附件或目标也影响动作，就必须一起绑定。正文不变但发送对象改变，已经是不同的授权范围。
2. **为什么 outbox 消息可能重复？** 分发器可能在远端成功后丢失确认，或收到确认却来不及保存标记。恢复仍会发送同一事件，下游应返回已有结果。
3. **旧状态缺少新版必填字段怎么办？** 从原请求和可靠记录恢复；例如金额 650 没有币种，无法判断时应补信息。不能随意填默认值并继续使用旧审批。

**实战案例：**

报告 v7 批准后，用户把附件替换为 v8。初版只保存 approved=true，恢复会发送新附件。处理时建立与 v7 动作摘要绑定的批准记录，将被替代请求标为 superseded；新动作重新走审批，批准后事务写入待发事件。验收时重放旧批准、替换附件、重复投递同一事件，分别确认旧批准不触发新动作、版本变化可追踪、重复投递不生成第二个业务对象。

</details>

**常见误区：**

把暂停等同于审批；把 hash 当作身份凭证；认为 outbox 提交意味着外部工单已经创建，或消费方可以不去重。

**微练习：**

写出发布动作摘要和审批状态转换，再列出 outbox 的四个故障窗口。验收：正文、收件人、附件任一变化都有明确处理，事件重复到达时可关联同一外部结果。

### Q062 租约、Fencing 与取消分别保护什么？

**优先级：P1**

**30–60 秒回答：**

租约帮助分配一段时间内的执行权，Fencing 由受保护资源拒绝陈旧执行者，幂等处理同一意图的重复请求。取消则先持久保存停止意图并阻止新的业务动作调度，已发出的远端动作还要对账。旧进程可能在租约过期后恢复，所以只在协调者里检查租约，不能自动保护真正的写入。

<details><summary>展开详细答案、追问与案例</summary>

**详细答案：**

长任务可能因进程暂停、网络分区或调度超时而交接。租约到期让新工作进程获得执行权，却不会物理删除旧进程已经持有的内存和连接。旧进程苏醒后仍可能提交动作，因此执行权分配与写入保护必须分开设计。给每次接管发放递增令牌，并让资源保存已见令牌、拒绝更旧值，才构成 fencing 的关键机制。

例如 A 持有 41 后暂停，B 取得 42 并完成受保护写入。A 再带 41 提交时，资源应拒绝它。这个保证依赖资源实际检查，而不是请求里多一个字段；也不能把“租约刚过期”直接等同于“资源已经见过新令牌”。外部服务不支持令牌时，若采用网关，必须保证写路径不可绕过，且校验与写入之间有一致性安排；先查租约再转发仍会留下竞争窗口。

取消也是一个持久状态转换。先记录取消，再停止安排新的业务动作；终态查询、对账和必要清理按允许范围继续。已发出请求可能成功，仍需记录结果并对账。若业务需要纠正已经产生的对象，应按明确权限执行后续动作，不能把本地状态倒回去当成外部事实消失。工程上分别测试陈旧执行、重复意图、取消后迟到结果，并用操作 ID、执行代次和外部对象串联证据；多个机制共同覆盖故障，而不是用一个“锁”包办所有语义。

**常见追问：**

1. **有 fencing 还需要幂等吗？** 需要。当前有效进程也可能因响应丢失重复提交同一动作；fencing 拦旧执行者，幂等识别重复业务意图，二者判断条件不同。
2. **取消成功是否表示没有外部副作用？** 只说明取消请求达到约定状态。还要区分未发出、执行中和结果已确认；对迟到成功结果保留记录并执行既定处理。
3. **数据库里的最大令牌能保护另一个 SaaS 吗？** 单独记录不能。要让真实写入路径参与检查或采用该服务可提供的条件写、幂等与查询机制，并描述剩余竞争窗口。

**实战案例：**

政策发布任务 A 暂停，B 接管后用令牌 42 更新报告状态；A 随后恢复，用 41 提交旧版本。测试存储拒绝旧令牌，避免覆盖 B。此时用户又取消任务，系统阻止后续发布调度，但此前已发出的工单请求返回成功，于是记录 T9 并进入对账。验收分别核对旧写被拒绝、取消后不再派发新的业务动作，终态查询、对账和必要清理按允许范围继续、迟到对象没有被伪装成不存在，三项证据不能由一个“任务已取消”字段代替。

</details>

**常见误区：**

认为租约过期会杀死旧进程；把令牌校验放在可绕过的入口；把停止等待当成撤销远端写入。

**微练习：**

画出 A 暂停、B 获得 42、A 苏醒、用户取消的时间线。验收：标出谁在何处拒绝 41，哪些请求已在途，如何识别重复意图，以及哪些结果仍需对账。
