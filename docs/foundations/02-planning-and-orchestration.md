# 规划、状态与多 Agent 编排

目标：画出可停止、可恢复、可解释失败位置的执行流程。

### Q009 最小 Agent Loop 应包含哪些环节？

**优先级：P0**

**30–60 秒回答：** 最小闭环是读取目标与状态、请求下一动作、检查动作、执行工具、记录观察，再判断继续或结束。模型只提出动作，程序负责工具白名单、参数验证、权限和预算。每轮都要有可追踪的状态变化；最终答案、等待输入、预算耗尽与不可恢复失败应该是不同终态，便于用户知道是否完成。

**追问与权衡：** 一次模型响应可能要求多个工具调用，不能假设“每轮恰好一个动作”。工具结果要能关联回对应调用。

**常见误区：** `while True` 加工具执行就完成系统设计；忽略无进展循环和工具副作用。

**微练习：** 手写六个状态及合法转移。验收：从每个非终态出发，都能解释如何到达完成、等待或失败状态。

### Q010 ReAct 与先规划后执行有何不同？

**优先级：P1**

**30–60 秒回答：** ReAct 将推理与环境动作交替组织，适合边获取信息边修正方向。先规划后执行会先形成任务分解，再执行和更新计划，适合依赖关系较清楚的任务。工程上可以让高层计划约束局部行动循环。计划要允许失效和重规划，否则前提变化后仍可能机械执行。[ReAct 原论文](https://arxiv.org/abs/2210.03629)

**追问与权衡：** 记录动作理由、计划摘要和实际证据即可支持许多调试任务；不应要求获得或公开模型隐藏思维链。

**常见误区：** 把工具调用次数多当作推理能力强；把任何“先想一想”的提示都叫 ReAct 实现。

**微练习：** 为“查资料后比较两个部署方案”分别写两条执行轨迹。验收：加入来源失效后，两种流程都能更新下一步。

### Q011 为什么用状态图组织 Agent？

**优先级：P0**

**30–60 秒回答：** 状态图把任务信息、执行节点和转移条件显式化。节点读取当前状态并产生更新，边决定下一步；这样能独立检查哪条路径会重试、请求人工输入或终止。图不会自动保证正确，它只是让控制逻辑更可见；业务不变量、状态字段约束和节点测试仍需自己定义。[LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)

**追问与权衡：** 状态只保存必要事实与引用。大文件放外部存储，图里存位置、版本和摘要，避免每次状态复制都携带巨量内容。

**常见误区：** 把所有节点都写成模型调用；支付、鉴权、计费等通常需要确定性代码。

**微练习：** 画 `接收→检索→校验→回答`，加入无权限、无证据和来源过期分支。验收：每条分支都有可观察结果。

### Q012 如何防止循环、反复重规划与无效重试？

**优先级：P0**

**30–60 秒回答：** 我同时设置步数、总耗时和资源预算，并检测进展，例如是否出现新证据、状态是否改变、是否连续重复同一参数调用。暂时错误可以有限重试，权限失败或非法参数应换处理路径。耗尽预算时返回当前完成项、未完成项和停止原因。单个“最大轮数”只能保底，无法识别很早就卡住的任务。

**追问与权衡：** 没有进展的判断要结合任务，重复查询有时是合理轮询，需要间隔与截止时间。

**常见误区：** 所有异常都交给模型自行修复，导致输入错误被不断重试。

**微练习：** 模拟工具连续返回同一错误。验收：给出第几次结束、结束码、保留的证据及用户可采取的下一步。

### Q013 多个分支何时可以并发？

**优先级：P1**

**30–60 秒回答：** 没有数据依赖且不会争用同一副作用资源的任务，可以考虑并发，例如分别读取两份公开资料。分支完成后必须明确合并规则、部分失败策略与超时处理。若多个分支更新共享字段，需要去重、冲突规则或串行化；仅把调用放进并发任务，并不能保证最后状态正确。[状态归并参考](https://docs.langchain.com/oss/python/langgraph/graph-api)

**追问与权衡：** 并发能减少关键路径时间，却可能放大速率限制、连接数和峰值成本。应限制同时进行的任务数。

**常见误区：** 对同一订单并行执行“退款”和“发货”；两次独立检查通过也不代表组合动作合法。

**微练习：** 两个分支分别返回 `[A,B]` 与 `[B,C]`。验收：写出有稳定顺序的去重结果，并说明一支失败时是否允许回答。

### Q014 Checkpoint 能保证恢复后不重复扣款吗？

**优先级：P0**

**30–60 秒回答：** Checkpoint 保存应用执行状态，便于恢复和人工介入，但它与外部支付系统不是天然同一事务。可能出现支付已成功、状态还没保存就崩溃，恢复后再次执行。需要由支付接口支持幂等键，并保存请求与外部操作标识；状态未知时先查询核对，再决定补偿或重试。[持久化参考](https://docs.langchain.com/oss/python/langgraph/persistence)

**追问与权衡：** 恢复时还要考虑代码版本、工具 schema 和权限变化。旧状态不能未经迁移直接假设适用于新执行逻辑。

**常见误区：** “框架支持持久化，所以已经实现 exactly-once”。

**微练习：** 列出“写入前崩溃”“远端成功但响应丢失”“状态保存后崩溃”。验收：每种情况说明查询、重试与幂等键如何配合。

### Q015 什么时候值得使用多个 Agent？

**优先级：P1**

**30–60 秒回答：** 先用单 Agent 或固定流程建立基线。若任务可以拆成较独立的子目标，需要隔离上下文或不同工具权限，多 Agent 才可能带来收益。成本包括任务分配、结果整合、重复工作和通信错误。是否值得，要看在相同验收规则下成功率、延迟与成本的变化，不能从角色数量推断系统更聪明。

**追问与权衡：** 独立评审可能减少某类错误，但多个相似模型也可能共享同一种偏差。讨论一致不代表证据正确。

**常见误区：** 把每个函数包装成一个“专家”，让简单任务被大量对话拖慢。

**微练习：** 对一个五步任务画单 Agent 与三 Agent 两版。验收：标出新增通信、可并行步骤以及需要什么实验才能证明拆分有效。

### Q016 多 Agent 如何交接，冲突如何处理？

**优先级：P1**

**30–60 秒回答：** 交接应像函数契约：明确目标、输入、约束、可用工具、预算、输出 schema 和完成条件。下游返回结论、证据引用、未解决问题与执行状态。协调者按预定义规则处理冲突，例如以最新有效版本或更高可信来源为准；无法判定就补充检索或请求决策，而不是按票数决定事实。

**追问与权衡：** 分工后权限仍应最小化。读取资料的 Agent 不应因为上游文字要求就自动获得发布或转账能力。

**常见误区：** 把完整历史无差别转发给所有 Agent，造成成本、污染和敏感信息传播。

**微练习：** 两个 Agent 对政策生效时间给出冲突答案。验收：用包含版本、来源、日期和置信边界的结构交接，说明如何裁决。
