# 04 · 工具循环：把一次决定变成可追踪的行动

## Agent 循环中的状态、观察与轨迹

**智能体循环（Agent Loop）是组织“观察、决定、行动、反馈”的反复执行过程。** 它解决的是一次模型响应之后怎样继续工作：需要更多信息就获取信息，需要补充条件就等待用户，达到要求才结束。

一轮开始时，程序读取**状态（state）**，也就是当前目标、已知条件、进度和剩余预算；模型或规则据此提出下一步。运行时检查动作后才执行工具，工具带回的实际信息叫**观察（observation）**。观察进入状态和下一轮输入，才有条件继续判断。

**提出动作、尝试执行和确认结果是不同的事件。** 将这些事件按任务关联保存，便得到可追踪的**运行轨迹（trace）**。模型提出工具请求，像填好一张申请单；运行时还要真的去办，申请单上的字再漂亮也不能代替执行结果。

本章沿[政策实验](../examples/policy_agent/README.md)的一次查询，依次看决定、校验、执行、结果回填与停止。可以先读本页的记录，再选做命令；旧执行器实验保留在文末选读。建议先读 [组成与协作](01-system-map.md)、[模型原理](02-llm-primer.md)和[提示与上下文](03-context-and-prompts.md)；运行代码时需要熟悉 Python 的函数与异常。

## 先定义循环的不变量

**不变量**是流程无论走到哪一步，都应保持成立的规则，例如动作只能来自允许的工具集合，预算不能因为重新规划就归零。它帮助我们检查整个循环，而不只检查正常路径有没有跑通。

内部政策助手接到问题后，一次迭代可以写成：观察当前状态→决定下一步→校验→执行→记录观察。决定可以是查询工具、提出澄清或结束。运行时检查工具是否允许、参数是否合法、当前身份是否获授权，以及预算是否够用，通过后才进入执行。

沿着这条链读：决定说明准备做什么，校验说明是否允许，观察说明实际取得了什么。程序也允许澄清、拒绝和结束，**不是每一轮都必须调用工具。**

显式保存状态与转移，能够让执行路径和恢复点可检查；但状态图本身不会保证业务正确。[LangGraph 状态、节点与转移参考](https://docs.langchain.com/oss/python/langgraph/graph-api) 对政策助手，已确认日期属于状态，检索结果属于观察，未知日期属于待补信息，实际工单是否存在属于环境终态。

至少要区分几种处理结果：已完成、等待补参、无权限、无法取得足够证据、预算耗尽及工具失败。等待意味着保存状态后还可以继续；完成或无法继续则需要明确停止原因。实际状态名称由程序定义，政策实验的终态与可恢复条件以其 [README](../examples/policy_agent/README.md) 和实际报告为准。

## 新实验：观察真正参与下一步决定

[![G3：一次工具请求和对应回包进入下一轮输入](../website/assets/diagrams/G3-tool-roundtrip.png)](../website/assets/diagrams/G3-tool-roundtrip.png)

图示应用侧工具返回后，再让模型处理结果的两轮模式。它不是每个工具必然增加两次外部模型请求的计费规则；托管工具可在平台内部执行，多个调用也可共享后续输入。下面的离线政策实验使用规则策略，不发出模型请求。

[政策实验](../examples/policy_agent/README.md)把策略输入限制为目标、条件、未知项和已经取得的可见观察；任务编号、故障标签和标准答案不进入策略。同一任务可以因观察不同而走出不同路径。

这里的**决策策略（policy）** 指“下一步怎样选择”的规则或模型，与案例中的报销制度文件不是同一个概念。下面按实际输入和观察，逐项判断合法下一步：

| 输入或观察 | 本轮动作 | 后续检查 |
| --- | --- | --- |
| 日期未知 | 请求补充 | 等待前工具调用数为0 |
| 条件齐全，尚无证据 | search_policy | 先看实际返回再决定 |
| 返回适用的新版住宿标准 | 引用条款并比较650与700 | 引用确实来自本次观察 |
| 工具提示资料已过期 | 重新读取指定日期适用的住宿标准 | 旧材料不能支撑当前结论 |
| 权威源仍无当前资料 | 证据不足结束 | 不编造700元 |

下面先沿正常路径看清这些环节，再改变输入和观察。完整入门过程也可以回看 [00 首次任务](00-first-agent.md)。离线策略读取观察来决定下一步，不测量真实模型的理解或规划能力。

## 沿一条政策查询轨迹读完一次循环

小明问：“2026 年 11 月 12 日去海岚出差，住宿每晚 650 元，超过普通员工金额上限吗？”可信档案提供员工类别，当前还没有取得制度。策略需要先查资料，再比较金额。

在仓库根目录运行；每个 `run-id` 对应一份保留目录，重做时换一个新名称：

```bash
python3 -m examples.policy_agent run --task 住宿金额核对 --mode offline --run-id loop-normal
```

仓库已有一份[正常路径的完整记录](../examples/policy_agent/traces/normal/trace.jsonl)。下表按其中实际的 `seq` 和 `event` 解释六条事件；这是阅读提纲，完整参数与结果仍以 JSONL 为准。

| 顺序 | 事件 | 发生了什么 |
| --- | --- | --- |
| 1 | `run_started` | 建立任务，标明离线模式与教学模拟 |
| 2 | `decision` | 策略提出 `search_policy` 请求 |
| 3 | `tool_started` | 运行时开始执行这次读取，`attempt=1` |
| 4 | `tool_result` | 这次查询返回新版住宿标准的有效条款，金额上限为 700 元 |
| 5 | `decision` | 策略根据已取得的条款提出带证据的回答 |
| 6 | `stopped` | 运行时完成输出校验，记录 `answered` |

在第 2 条与第 3 条之间，运行时检查工具名、参数、当前身份与调用预算，再把合法请求排入待执行队列。成功的每项检查并不会各记一条事件，所以阅读轨迹时还应对照[执行器实现](../examples/policy_agent/core.py)。`decision` 表示已经提出请求，`tool_started` 才说明进入了执行环节。

第 4 条的结果被写入任务观察，组装下一轮输入时再提供给策略。于是第 5 条可以使用“11 月 12 日适用新版标准、金额上限 700 元”作答。只把结果记进日志、却不放入后续输入，下一步就无法据此判断。实际输入可对照[正常路径的上下文快照](../examples/policy_agent/traces/normal/context.json)，输入选择的原理在 [第 03 章](03-context-and-prompts.md)中解释。

最后，运行时核对主张与有效证据，再按用户金额计算并渲染比较结果：650 ≤ 700，本例金额条件未超限。`answered` 表示这次查询已经作答；用户没有要求创建工单，后端也应没有新对象。判断任务完成，需要同时看回答、依据和实际结果。

## 决策次数、工具调用与执行尝试怎样计数

打开本次运行的 `.local/policy_agent/loop-normal/result.json`，可看到以下计数。仓库保存的[正常结果](../examples/policy_agent/traces/normal/result.json)使用相同口径：

| 字段 | 正常路径的值 | 统计对象 |
| --- | --- | --- |
| `decisions_used` | 2 | 两次策略决定：提出检索、提出回答 |
| `tool_calls_started` | 1 | 已开始的逻辑工具调用，这里仅查询一次 |
| `attempts_by_call_id` | 按调用标识记录的映射；本次调用对应 1 | 每次调用实际尝试执行的次数 |
| `model_requests_used` | 0 | 真实模型请求数；离线规则没有发出模型请求 |
| `created_count` | 0 | 模拟后端新建的工单对象数 |

因此，六条事件对应两次决定、一次工具读取。工具执行若发生重试，同一个调用标识下可以有多次尝试；这些数不能仅靠日志总行数相互换算。

## 观察变化时，循环怎样改变

先改变必要条件，再改变工具观察，可以分别看见等待与补查的作用。

```bash
python3 -m examples.policy_agent run --task 住宿金额核对 --variant missing-date --mode offline --run-id loop-missing
```

缺少日期时，第一次决定请求补充 `trip_date`，随后记录 `waiting`，状态为 `clarification_required`。此时没有检索、没有写入。先看等待时的 `context.json` 和 `result.json`，再补充日期：

```bash
python3 -m examples.policy_agent resume --run-id loop-missing --reply-json '{"trip_date":"2026-11-12"}'
```

恢复记录先出现 `state_updated`，再进入检索、工具结果与回答；累计三次决定、一次工具调用，预算没有因为恢复归零。`context.json` 是最近一次快照，恢复后会更新，等待阶段仍可沿[补参轨迹](../examples/policy_agent/traces/missing-date/trace.jsonl)回查。补日期提供了事实，没有授予创建工单的批准。

```bash
python3 -m examples.policy_agent run --task 住宿金额核对 --variant stale-first --mode offline --run-id loop-stale
```

这次第一次读取返回旧版住宿标准，状态为 `stale_evidence`。新的观察使策略提出 `get_policy`，核对指定日期后取得适用的新版标准，才继续回答。[实际轨迹](../examples/policy_agent/traces/stale-first/trace.jsonl)累计三次决定、两次工具调用，模型请求和新建工单仍为零。如果权威源始终没有当前材料，就应按证据不足结束，而不能填入记住的 700 元。

两条变式保留了同一个目标。变化发生在未知条件或实际观察中，下一步也随之改变，这正是循环中反馈的作用。

## 保存进度与核对终态

本政策实验用`pending_calls`（待执行调用）和下一待执行索引保存调用队列位置。暂停后恢复，应复用已确认的结果；结果未知的写入先查询或对账，不能仅凭队列位置判断是否重做。累计六次决策预算也不能重置。其他运行时可以采用不同状态结构，可恢复不等于允许无限重试。

查询任务看条款与比较结果，写入任务还要看后端对象。更完整的批准、结果未知与跨进程恢复在[政策实验](../examples/policy_agent/README.md)和[持久执行](../advanced/02-durable-execution.md)展开；这里先把每次决定怎样接到执行和下一轮输入讲清。

## 用自己的话说明一次循环

合上正文，画出“状态 → 决定 → 校验与执行 → 观察 → 下一轮输入”，分别标出策略、运行时和工具。再完成三件事：

1. 从正常轨迹找出工具结果进入下一次决定的位置，解释为何有六条事件却只有两次决定。
2. 预测缺日期时的处理状态和工具调用数，再说明补参后怎样继续。
3. 对照旧证据变式，指出哪一条观察触发了补查，以及回答最终引用哪份条款。

<details><summary>核对你的解释</summary>

1. 第 4 条是 `tool_result`，第 5 条是利用该结果的 `decision`；两条 `decision` 统计两次决定，其他事件记录启动、执行、返回与停止。
2. 应等待补充日期，工具调用数为 0。可信回复更新保存状态后，累计预算沿用，再进行检索和回答。
3. 第一次 `tool_result` 返回 `stale_evidence`，随后提出 `get_policy`；取得有效版本后引用新版住宿标准的金额条款。

</details>

## 旧执行器实验中谁在做什么

打开 `lab.py`，先读 `Action`、`Finish`、`State` 和 `RunResult`。`Action` 保存工具名与参数；`Finish` 表示策略希望结束；`State.observations` 保存已成功取得的工具结果；`RunResult` 汇总停止原因、事件与尝试次数。

再读 `scripted()`：它从预先给定序列取下一项，忽略传入状态。即使搜索返回另一份材料，它也照着预写序列往下走；`loop` 场景同样使用固定 lambda。这些替身便于把控制路径重复跑出来，真实 LLM 的规划、自然语言理解和工具选择效果还需要另外测量。

`run()` 管理步数和错误分支；`Runtime.invoke()` 在执行边界调用 `validate()`，检查工具白名单、字段与取值，写路径还要匹配运行时配置的 `Approval`。`search` 只对四条英文样例文本按关键词交集排序，既不是语义检索，也没有真实制度库。工单只存在同一进程的字典里，当前代码没有用户认证、租户对象权限或操作系统安全隔离。

这个选读实验把场景缩成“查询教学条目”，便于沿固定事件检查边界。正文的政策实验另有固定制度数据与观察驱动策略；真实模型路径按其验证记录单独判断。

## worked example：沿一次真实 trace 走到底

以下回到旧执行器实验 `agent_lab/lab.py`，与前面的政策实验使用不同的事件名和计数。在仓库根目录执行：

```bash
python3 examples/agent_lab/lab.py --scenario happy
```

第一步，脚本提出搜索请求，记录 `decision`；运行时检查并执行后，才把找到的教学条目记为 `observation`。第二步，脚本给出固定的结束动作，运行时记录停止并汇总。下面将关键事件转成阅读提纲，原始输出可通过上面的命令核对：

| 事件 | 表示什么 |
| --- | --- |
| 决定 | 脚本提出查询请求 |
| 观察 | 实际取得讲解工具循环的教学条目 |
| 停止 | 固定脚本结束本次执行 |

汇总的 `steps=2`、`search_attempts=1`、`created_count=0`。先对照事件数：搜索决定占一步，结束决定再占一步，真正的搜索尝试只有一次。这样读就能看出策略步数和工具尝试数各自在数什么。

最后文本预先写在脚本中，控制器没有独立检查引用是否支持回答。因此，这个结果验证了固定轨迹按预期结束；要评价回答质量，还需检查证据蕴含和真实模型的行为。

## 失败时，计数和终态如何变化

再在仓库根目录运行以下命令：

```bash
python3 examples/agent_lab/lab.py --scenario denied
python3 examples/agent_lab/lab.py --scenario retry
python3 examples/agent_lab/lab.py --scenario loop
```

`denied` 先记录创建工单的决定，但没有匹配的运行时批准，随后记录 `tool_rejected` 并以 `approval_required` 停止。创建数和写尝试数均为零。这里证明批准检查阻断了模拟写路径，不证明完整用户鉴权已实现，也没有交互式审批页面。

`retry` 在同一步首次检索暂时失败，第二次成功，再到第二步结束。其 `steps=2`，`search_attempts=2`。每次读调用最多尝试两次，包含首次；这与策略步数是不同预算。实验只有这一类暂时读错误会自动重试，没有退避计时、真实网络或总期限。

`loop` 连续检索三次，第三步后以 `step_budget_exhausted` 停止，不再向策略索取第四个决定。它验证步数上限，却没有验证 token 预算、并发配额或取消。缺字段则会成为 `invalid_arguments`；实验会停止，不会自动向用户追问。若要实现澄清分支，应新增状态和交互，而不是只改报错文本。

运行 `python3 examples/agent_lab/lab.py --scenario approval`，观察同一批准意图提交两次的结果：汇总是 `write_attempts=2`、`created_count=1`，第二次观察带有 `replayed=true`。前者统计进入模拟写路径的次数，后者统计后端字典实际对象数。

把它迁移到政策咨询场景，先分清用户是在重试，还是确实要再建一条。内容相同但业务意图独立的新工单，应使用新的操作标识；响应丢失后重试同一意图，则保留稳定标识以便核对。

当前实验只展示同一运行时里的顺序去重，进程重启后字典就消失。检查结果时要一起看计数、对象标识和内容，才能判断验证的是顺序重放，还是跨重启恢复等其他能力。

## 从 trace 读取执行结果

事件记录应让人区分“提出动作”“执行成功”“执行被拒”“结果未知”。特别是写操作超时，环境可能已经改变；旧lab通过替身验证部分不确定写入情景；跨进程持久恢复另见政策实验的工单崩溃恢复场景。[实验能力边界](../examples/agent_lab/README.md) 不要把 trace 的最终字符串直接当作外部环境证据，也不要把缺少观察当作没有副作用。
