# 06 · RAG 与检索

<div id="rag-到底是什么"></div>
<div id="为什么需要先找资料"></div>

**RAG 是在回答时，把检索到的外部资料交给模型。** 资料可以来自文档、搜索索引或数据库。新资料要先进入可查询的数据源，后续请求才有机会取到。更新资料和微调模型是两项独立的工作。

理解这条链路，要分清三份内容：**检索找到了什么、筛选后留下了什么、模型实际看到了什么。** 排查时，可以沿着这三份记录找到证据丢失的位置。

<div id="两条链路要分别设计"></div>

## 入库与查询

**入库**负责把原文变成可查的资料。系统解析正文和表格，再把内容切成片段。每个片段保留来源和版本。处理完成后，系统发布索引。

**查询**负责为当前请求取资料。系统先找候选，再筛选和排序。选中的片段进入模型输入。回答生成后，再核对关键结论与引用。

[![RAG 的入库与查询流程](../website/assets/diagrams/G5-rag-pipelines.png)](../website/assets/diagrams/G5-rag-pipelines.png)

排查时，先看查询实际用了哪一版索引。再确认所需资料已经发布到这版索引中。资料还没进索引时，扩大召回范围也只能查找已有内容。

<div id="文档片段和索引各保存什么"></div>

## 分块与索引

**分块决定了哪些内容可以被单独找到。** 每个片段都应能追溯到原文位置和文档版本。标题、表头、单位和适用条件也要保留。它们会影响正文的含义。

- **片段太小**，结论容易和限定条件分开。
- **片段太大**，多个主题容易混在一起，也会占用更多输入空间。
- **相邻片段重叠**，可以减少边界上的信息丢失。重叠越多，去重的工作也越多。

有时小片段更容易被找到，完整证据却在它所在的大段落里。可以先定位小片段，再按需读取原段落。扩大读取范围时，要核对原文版本和访问权限。

<div id="稀疏与稠密检索分别看到什么"></div>

## 关键词检索与向量检索

### 关键词检索

关键词检索先把文本处理成可匹配的词。倒排索引记录每个词出现在哪些片段里。查询时沿这份记录查找，省去了逐篇阅读全文的工作。

**BM25** 是一种常见的排序方法。它会考虑词出现的次数、词有多稀有，以及片段有多长。同一个词重复出现，得分的增幅会逐渐减小。

编号、产品名和专有词通常适合用关键词匹配。中文分词会直接影响这些词能否被找到。

### 向量检索

向量检索把请求和文档片段转成向量，再按相似度或距离查找。文档向量可以提前算好。查询向量与文档向量需要处于兼容的表示空间。更换编码器后，通常要重新计算文档向量，再验证检索结果。

精确搜索按选定的度量寻找最近的向量。近似搜索减少了计算量，也可能漏掉部分近邻。排查这类损失时，先固定向量和度量，再与精确搜索对照。找到更接近的向量之后，还要核对其中有没有回答所需的证据。

<div id="手算一次混合检索"></div>
<div id="为什么召回和重排要分开"></div>

## 召回、融合与重排

| 环节 | 负责的工作 |
| --- | --- |
| **召回** | 从大量资料中找出一批候选。 |
| **融合** | 合并多路检索结果。 |
| **重排** | 重新给已有候选排序，让更相关的片段靠前。 |

关键词检索和向量检索的分数通常使用不同的尺度。**RRF（倒数排名融合）**按名次合并结果。每一路按 `1 / (常数 + 名次)` 给片段计分，名次从 1 开始。片段出现在多路结果中，就累加各路得分。

**候选集合固定时，重排只能调整顺序。** 缺失的材料要通过补查或补读取得。重排通常需要逐条判断候选。候选越多，这一步的工作量通常也越大。

<div id="从融合结果到回答逐步核对"></div>

## 证据筛选与模型输入

候选资料要经过三项判断：

- **访问权限**决定当前用户能使用哪些资料。
- **适用条件**决定资料能否用于本次任务。重点核对日期、版本和对象。
- **相关性**决定哪些候选优先阅读。

搜索前就可以按权限和日期缩小范围。正文交给外部重排服务或模型前，必须完成访问检查。读取旧索引或缓存时，也要按当前权限判断。

整理模型输入时，先去掉重复片段。再为支持结论的必要材料留出空间。缩短文字时，要保住日期、单位和例外条款。核对时直接看送进模型的文字，确认这些条件还在。

<div id="找到相互矛盾的材料时怎么办"></div>

### 处理资料冲突

先检查两份资料是否描述同一对象、同一时期和同一适用范围。条件不同，就分别按各自的范围处理。

条件一致时，再查原文来源、正式的取代关系和来源优先级。**上传时间和生效时间要分别记录。** 两份同级资料都适用，结论却互相冲突时，应保留双方出处，并说明分歧。

<div id="原文标注与回答放在一起核对"></div>

## 回答与引用核对

引用链接用来定位出处。核对时，要读到具体段落。逐项确认关键结论能否从原文推出。用到多个片段时，再检查它们的日期、对象和范围能否一起成立。

缺少资料，就围绕缺口补查。缺少用户条件，就请用户补充。达到查询上限后，给出已有证据能够支持的结论，并说明剩余的缺口。

<div id="分别评价检索与回答"></div>
<div id="练习定位一个搜到了却答错的案例"></div>

## 分阶段排查与评测

排查时，用**片段编号和资料版本**串起各阶段的记录。先确认预期资料已经发布、当前可访问，也适用于本次任务。再沿实际执行顺序查找偏差。

| 看到的情况 | 先查哪里 |
| --- | --- |
| 原文有关键内容，索引中的片段却不完整 | 解析、分块和索引发布 |
| 资料已经入库，预期片段没进候选 | 查询写法、搜索范围和召回方式 |
| 片段进了候选，随后被移除 | 权限、适用条件和筛选原因 |
| 片段通过筛选，却没完整进入模型输入 | 排序、去重和截断 |
| 模型收到了完整证据，回答仍有偏差 | 模型对证据的使用，以及结论和引用 |

比较检索方案时，使用同一批请求。固定资料版本、访问范围和模型输入上限。分别记录以下结果：

- 找回了多少所需证据。
- 多少证据完整进入了模型输入。
- 多少关键结论得到了支持。
- 执行耗时多久，调用了多少次工具。

**Recall@K** 用来衡量前 K 个候选的覆盖情况。用前 K 个候选里找到的相关证据数，除以该请求已标注的相关证据总数。对于本来就没有可用证据的请求，单独检查系统是否能识别资料不足。

扩大候选范围后，如果找回的证据变多，最终输入却没有改善，就回查筛选、排序和输入整理。每次只改一个主要环节，结果更容易解释。
