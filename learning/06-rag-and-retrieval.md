# 06 · RAG 与检索：从资料入库走到有依据的回答

[上一章：工具与 MCP](05-tools-and-mcp.md) · [学习目录](README.md) · [下一章：记忆与状态](07-memory-and-state.md)

## RAG 到底是什么

**RAG 是 Retrieval-Augmented Generation 的缩写，中文叫“检索增强生成”：先从外部资料中找出相关内容，再把这些内容提供给语言模型，让它据此组织回答。** 外部资料可以是公司制度、产品手册或其他可查询的数据；选中的内容会进入模型本次调用的上下文，也就是这一次实际提供给模型的信息。

把这个名字拆开，就能看清它在做什么：

- **Retrieval，检索**：根据问题去资料源中找候选内容，回答“参考材料在哪里”。
- **Augmented，增强**：筛选材料，把需要的段落和问题一起放进模型输入，补上本次回答需要的信息。
- **Generation，生成**：模型读取问题和这些材料，组织答案；需要引用时，还要保留结论对应的出处。

可以把这个过程理解为**带资料的开卷答题**：检索负责找参考页，应用把选中的段落摊在桌上，模型再读材料作答。开卷也会翻错书，所以“找到了材料”和“答对了问题”还得分别检查。[检索与生成的关系](https://docs.langchain.com/oss/python/deepagents/retrieval)

## 为什么需要先找资料

模型训练时接触过的知识，未必包含公司的内部制度，也未必包含刚发布的产品说明。即使模型能把话说得很顺，回答这些问题仍需要本次适用的资料。**RAG 在回答时补入当前检索到的资料，帮助模型使用私有或更新后的信息。** 文档更新后，可以更新资料及索引，再让后续查询取得新内容。

这里要分清几件事：**检索**把候选资料找出来，**RAG**把选出的资料接入生成过程；**微调**则通过训练修改模型参数。一次检索和输入装配不会自动改动参数，RAG 也可以与微调配合使用。原始 RAG 研究结合了模型参数中的知识与外部检索记忆；本章讲的是工程中常见的基本过程，不要求照搬原论文的训练架构。[RAG 原始论文](https://arxiv.org/abs/2005.11401)

RAG 可以放进固定工作流，也可以由 Agent 按任务需要触发。检索方式可采用关键词、向量或其他适合资料的查询方法。**它提供的是使用外部证据的路径，回答是否正确仍取决于材料和使用过程。**

读完本章，应能分开描述入库与查询链路，手算一个混合检索结果，并定位为什么有检索仍会答错。建议先读 [工具调用](05-tools-and-mcp.md)和[模型原理中的 Embedding 说明](02-llm-primer.md)，了解调用边界与向量检索的输入输出。

## 两条链路要分别设计

**入库**是把原始资料整理成可检索内容的准备过程。长文通常会拆成**片段（Chunk）**，方便按问题取用；**索引（Index）**帮助检索器定位候选内容；**元数据（Metadata）**记录版本、生效日期、来源和权限等信息，用来判断一段文字在什么条件下可用。

**入库链路**处理资料如何变成可检索对象：接收政策、解析正文与表格、清理重复、按语义边界分块、附带元数据、建立稀疏或稠密索引。元数据至少考虑政策 ID、版本、生效日期、章节、来源链接和访问范围。分块太小会切断适用条件，太大可能稀释关键内容；块大小是需要实验的参数，不存在对所有文档都最优的固定数字。

查询时，**召回**先找出一批可能有用的候选；用了多种检索方法，可以通过**融合**合并它们的候选或排名；**重排（Rerank）** 再根据问题与候选内容调整顺序。这些步骤帮助挑材料，最后还要判断材料是否适用。

**查询链路**从这次问题和可信身份出发，在授权范围内生成检索条件、召回候选，再做融合或重排，并核对版本与适用日期。随后按问题覆盖和预算选择证据，构造上下文，生成回答并校验引用，必要时拒答。

入库链路准备了可检索的材料，查询链路还得为眼前这个问题选对材料。数据库内部可以按实现先取得候选标识再过滤，但**无权正文不能因此先交给生成模型或外部重排服务**。

排障时一起保存问题、索引版本、候选列表和最终使用的片段。候选里压根没有现行制度，应往检索之前查；候选齐全但最终没用上，再看排序、筛选和生成。最后一句回答再流畅，也不能替这些阶段提供证据。

精确搜索可作为对照基线；近似最近邻索引通常用一定召回取舍换速度，效果需要实测。过滤位置还会影响有效候选数：例如 pgvector 文档说明，某些近似索引扫描后再过滤，可能不足要求的结果数，可借助迭代扫描寻找更多候选。不要把此执行顺序推广到所有向量库；无论怎样优化，无权正文都不能先进入模型。[pgvector 过滤说明](https://github.com/pgvector/pgvector#filtering)

## 原文、标注与回答放在一起核对

在住宿政策助手中，检索可能找到了相关段落，甚至给出很高的相似度分数，小明却发现引用来自旧版制度。也可能版本没错，片段却漏掉了“仅适用于管理人员”。下面用同一份虚构制度，把检索、选证据和回答逐步对应起来。

![G5：入库准备文档和索引；查询取得候选、筛选适用证据、组装输入并生成回答](../website/assets/diagrams/G5-rag-pipelines.png)

[查看原图](../website/assets/diagrams/G5-rag-pipelines.png)

小明是普通员工，准备2026年11月12日去海岚出差，问：“酒店每晚650元，超过住宿标准吗？”回答这句话，需要先找到**对这个城市、日期和员工类别适用的金额条款**。

检索取得的虚构原文是：“普通员工海岚住宿金额上限为每晚700元”，从2026年11月1日起有效。它的来源标识是 `P17-v2#4`，表示P17文档第2版第4条。把这段材料和问题交给模型后，才有依据比较650元与700元。

**标注**是评测时事先记录的参考材料与正确条件，用来核对实际检索和回答。这里不能只把片段标成“相关”，还要核对城市、普通员工类别（实验字段为 `staff`）、出行日期和读取范围。若把日期改成10月31日，适用依据会变成旧版 `P17-v1#4`，其上限为600元。

| 问题条件 | 必须取得的证据 | 可支持的回答 |
| --- | --- | --- |
| 2026年11月12日，海岚普通员工，650元 | P17-v2#4，700元 | 本例金额未超限 |
| 2026年10月31日，海岚普通员工，650元 | P17-v1#4，600元 | 本例金额超过上限 |
| 2026年11月12日，海岚普通员工，800元并询问例外咨询 | P17-v2#4与P20的材料条款 | 超出金额标准；咨询需日期、城市、金额、事由；咨询不等于批准 |

引用回答示范：“按P17-v2第4条，2026-11-12海岚普通员工上限为700元/晚；650元未超过该金额上限。”这句话刻意限定到金额条件，没有推断其他真实报销资格。

再做一次漏召回：让候选只有P22办公制度。即使排序第一、分数最高，也没有住宿证据。**候选里分数最高的片段，也可能不足以回答问题。**

想运行验证时，上表三行分别对应仓库实验中的 `T01`、`T02`、`T06`。选择 `T01/empty-result` 或 `T01/no-current-source` 应得到证据不足；`stale-first` 则允许追加权威查询。这些数据变式检查证据使用，不把本地词项过滤称为生产语义检索。[固定资料与变式](../examples/policy_agent/README.md)

## 稀疏与稠密检索分别看到什么

**稀疏检索**常根据词项及其权重匹配，适合制度编号、专用名词等线索；效果取决于分词和检索配置。**稠密检索**把问题与片段编码为向量，比较其表示，可能帮助匹配不同措辞。把文本变成数值表示的过程，通常称为 **Embedding（嵌入）**；这里的向量是一组用于比较的数字。

DPR（Dense Passage Retrieval，稠密段落检索）的双编码器，就是将问题和段落映射到可比较空间的一种方法。[DPR 原始论文](https://arxiv.org/abs/2004.04906)

“可比较”要求表示空间兼容，长度相同只是其中一个条件。可以使用同一编码器，也可以使用联合训练的查询/文档编码器；两套无关模型生成的等长向量不能直接混用。文档换了 embedding 模型，通常需要相应重建索引并验证查询端兼容性。

可以借坐标图记住这件事：两张纸都画了横纵轴，不代表它们的原点、方向和单位相同。对应到检索，向量维度相同，还要确认编码器让这些坐标具有可比较的含义。这个类比说明兼容性，具体相似度仍由模型和距离约定决定。

例如两个单位向量 `(1,0)` 与 `(0.8,0.6)` 的余弦相似度是 `0.8`。它表达方向接近程度，**不是“答案有 80% 概率正确”**，也不能直接跨模型当成统一置信度。相似度阈值应在目标数据上校准，还要结合版本、适用条件与证据是否充分。[余弦相似度定义](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.pairwise.cosine_similarity.html)

## 手算一次混合检索

小明问：“去海岚住每晚 650 元，超标准能申请吗？”关键词搜索可能抓住城市与“超标准”，稠密搜索可能找到“例外审批”。假设两路检索得到以下排名：

| 片段 | 内容角色 | 稀疏排名 | 稠密排名 |
|---|---|---:|---:|
| A | 现行住宿标准与适用类别 | 1 | 未入选 |
| B | 差旅系统填写说明 | 2 | 2 |
| C | 超标准住宿的例外审批 | 3 | 1 |
| D | 历史问答记录 | 未入选 | 3 |

不同检索器分数尺度可能不同，直接相加不一定合理。**RRF（Reciprocal Rank Fusion，倒数排名融合）** 使用排名来合并结果：对每个候选累加 `1/(c+rank)`，排名从 1 开始，未出现在某一路的候选在该路贡献为 0。这里取常数 `c=60` 与仓库实验保持一致。[Elastic RRF 文档](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

```text
A = 1/61        ≈ 0.01639344
B = 1/62 + 1/62 ≈ 0.03225806
C = 1/63 + 1/61 ≈ 0.03226646
D = 1/63        ≈ 0.01587302
融合顺序：C → B → A → D
```

这一步只汇总两个排序对候选的支持，尚未判断制度是否有效。重排器可以进一步逐对比较“问题—候选”，调整桌上这些材料的顺序；若片段 E 根本没被拿到桌上，这轮重排就无从比较它。排查遗漏时先看召回集合，别让重排器背一口它接不住的锅。[Sentence Transformers 检索与重排](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

## 从融合结果到回答，逐步核对

第一步，把问题拆成“适用住宿上限”和“例外路径”，确认日期与员工类别。第二步，只在小明允许查看的政策范围检索；权限条件来自可信身份，不来自模型生成的租户名。第三步，融合后 C、B 靠前，但住宿标准 A 仍是必要证据，不能只拿前两项就认定证据完整；继续重排与筛选，并核对版本、生效区间与适用对象。历史问答 D 不能覆盖现行制度。

第四步，选取 A 的金额规则与 C 的审批条件，保留章节和来源。假如 A 只写管理人员标准，而小明类别未知，正确动作是澄清，不是挑一个看似合理的数字。第五步，生成“在这些条件成立时适用某标准；例外需怎样申请”的回答，关键断言分别指向 A、C。引用链接存在不够，**原文必须实际支持相邻结论**。

第六步，校验来源当前仍可访问。权限撤回和政策更新需要影响索引、缓存与引用原文入口，不能只改前端按钮。授权应在正确的资源访问边界执行；即使某结果不会显示给用户，也不能先把无权正文送入模型再希望它保密。[OWASP 授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

第七步，若现有证据无法覆盖用户条件，应说明缺口、请求补充或转人工。一个“没有足够证据”的正确结果，比将检索相关性误当成事实正确性更符合任务目标。**检索评测检查材料是否找对，回答评测检查材料是否用对，两者需要分别测量。**

## 练习：定位一个“搜到了却答错”的案例

准备 6 条虚构政策片段：现行标准、旧标准、例外流程、无关制度、不同员工类别和无权限资料。手工给 4 个问题标注相关且允许使用的片段，写出两路排名，按上式融合。故意把正确片段从两路候选中删除，再尝试重排。

**验收：** 能复算融合顺序；能指出重排无法修复哪一种遗漏；每个回答标注证据及版本；无权限片段不进入生成上下文；条件不足时明确拒答或澄清。可参考 [基础数学实验说明](../examples/foundations/README.md) 做手算对照，不依赖某个 SDK。

## 自检

1. 余弦分数 0.9 是否表示回答正确率 90%？
2. 向量库召回了旧政策，错一定在模型吗？
3. 加了重排器，Recall 一定更高吗？

<details><summary>参考答案</summary>

1. 不是，它是向量相似度；正确性需要目标任务证据与评测。
2. 不一定，可能是更新、元数据过滤或证据选择问题，应沿链路定位。
3. 不一定。它在候选范围内排序，无法找回未召回项；截取最终 top-k 还可能改变该截断位置的召回表现。
