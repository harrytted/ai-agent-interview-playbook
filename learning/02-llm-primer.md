# 02 · 大模型最小原理：从 token 到一次生成

本章目标是解释政策助手的一次模型调用：文本怎样进入模型，注意力怎样使用历史，生成为什么需要多步。先修为第 01 章和基本概率、向量加权平均。核验日期为 **2026-10-28**；公式仅描述明确限定的模型机制，不以某个服务的价格、上下文长度或接口为前提。

## 文本先变成 token

模型通常不直接把整句自然语言当作一个不可拆对象。分词器按照自己的词表与规则，把文本编码成 token ID；生成后再解码回文本。一个 token 可以对应词片段、字符或其他字节组合。中文、英文、标点和代码的切分并不一样，不能用“一个汉字固定等于几个 token”做容量承诺。实际预算应使用目标模型对应的分词器或服务返回的用量；更换模型后重新核对。

对虚构问题“培训住宿能报销吗”，本课程不凭空给出真实 ID。可以先画一排标记表示编码结果，但它只是示意。若要实际测量，应记录模型和分词器版本、原始字符串及编码结果；不要拿另一套词表生成的数字冒充当前模型的计数。[Hugging Face 分词资料](https://huggingface.co/docs/transformers/tokenizer_summary)

## 生成是在条件分布上逐步选择

对典型自回归语言模型，已有序列为前缀，模型计算下一个 token 的条件分布，再由解码策略选择输出，接着把新 token 加入前缀。整个序列的概率可以分解为各步条件概率的乘积。这说明一次长回复通常包含多次生成步骤；它不是一次从数据库读出完整答案。[Hugging Face 生成机制](https://huggingface.co/docs/transformers/llm_tutorial)

例如，教学词表里第一步输出“可以”的概率是 0.6，选到后下一步输出“报销”的条件概率是 0.7，那么这个两步路径的联合概率是 0.42。数字只展示链式法则，没有来自任何真实模型。更关键的是：即使某条文字路径概率很高，也不能据此证明员工确实满足报销条件。事实需要有效政策与人员、日期等输入支撑。

温度和采样方式影响如何从分布选择 token，但不是事实认证开关。政策证据缺失时，换一种采样方式不会凭空补出可信的制度版本。因此，要同时观察语言生成与任务验收，不用“输出稳定”代替“结论正确”。

## 因果注意力的一个小算例

标准注意力把表示投影成 Query、Key、Value：当前 Query 与各 Key 计算匹配分数，经缩放和归一化后，对 Value 加权。因果遮罩不让当前位置直接看到未来 token。这个机制是标准 Transformer 的一部分，完整网络还包括多头、位置相关设计、残差和前馈层等。[Attention 原论文](https://arxiv.org/abs/1706.03762)

现在做一个原创的极简算例：只保留一头、一维，Query 为 1，两条可见记录的 Key 为 0 与 `ln(2)`，Value 为 3 与 9。一维缩放因子为 1，得分为 0 与 `ln(2)`；指数为 1 与 2，归一化权重为 1/3 与 2/3，因此输出为 `3×1/3+9×2/3=7`。若第三条记录属于未来位置，其得分要被遮罩，不参与有效权重。这是在算一次信息混合，不是把“7”当成报销结论。

以下是**可运行 Python**，只依赖标准库，已实际运行验证；另一组二维算例见 [基础数学实验](../examples/foundations/README.md)。这些脚本均不加载真实模型。

```python
import math

scores = [0.0, math.log(2.0)]
weights = [math.exp(x) / sum(math.exp(s) for s in scores)
           for x in scores]
output = sum(w * v for w, v in zip(weights, [3.0, 9.0]))
assert math.isclose(output, 7.0)
print(round(output, 6))
# 7.0
```

## 为什么要区分 Prefill、Decode 与 KV Cache

已有输入进入模型时，要处理它们的表示；自回归生成开始后，再逐步产生新 token。常见服务将这两个阶段称为 Prefill 和 Decode。对常见因果注意力实现，KV Cache 保存过去位置的 Key 与 Value，以减少重复计算，但需要额外存储空间。[缓存机制参考](https://huggingface.co/docs/transformers/cache_explanation)

政策助手的问题很短，检索材料却可能很长，因此首 token 等待与后续生成速度可能受不同因素影响。应分别测输入长度、输出长度、首 token 时间及完成时间。KV Cache 是一次计算的中间表示，不是员工偏好档案，也不是把新制度训练进模型。它是否跨请求复用、如何失效，要看具体服务实现，不能由“支持缓存”几个字推断。

## Embedding、训练方法与应用改动

检索常把文本编码成 embedding，再按某种距离找候选；生成模型则根据上下文产生后续 token。二者任务与输出不同，模型、维度和距离约定要匹配。相似度是相关性信号，不是答案真实性分数；政策编号只差一位时，精确匹配可能仍然关键。[检索编码与重排参考](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

训练概念也要分维度：预训练描述广泛学习过程；SFT 用示范数据学习目标行为；偏好优化利用偏好信息；LoRA 则描述一种参数高效适配方式，不能与 SFT 当作互斥阶段比较。[SFT](https://huggingface.co/docs/trl/sft_trainer)、[DPO](https://huggingface.co/docs/trl/dpo_trainer)、[LoRA](https://arxiv.org/abs/2106.09685) 对每天变化的政策，首先应检查知识更新与检索链路；对稳定的输出行为问题，再用实验决定是否微调。这里是问题定位建议，不承诺某方法必胜。

用案例区分两类改变：把政策新版放入检索库，是改变推理时可取得的材料；用标注样例训练模型，是改变参数。员工纠正了一次答案，应用可以记录反馈，但这条消息不会因此自动触发梯度更新。若团队确实建立了反馈训练流水线，还需要清洗、授权、数据版本和独立验证，不能把“能记日志”称为在线学习。

阅读模型说明时，可以沿输入、参数与输出三条线检查。输入侧问分词器是什么、材料是否完整；参数侧问采用哪个模型版本、是否额外适配；输出侧问解码限制、字段校验和验收方式。这样遇到错误时，能先定位“输入没有政策”还是“模型误读了政策”，再决定改检索、提示或训练，避免把所有故障都交给更大的模型。

## 动手验收

不用真实模型，先把注意力算例的 Value 从 `[3,9]` 改为 `[3,0]`，预测结果后运行，记录答案应为 1。然后为政策助手画两条路径：“文本→检索向量→候选文档”和“上下文→逐 token 生成→答案”。验收时分别标出输出类型、版本信息与一种失败条件；如果把 embedding 当成最终答复，或把缓存当成长期记忆，需要重画。

## 自检

1. 能否承诺任何中文模型都按同一汉字比例计费？
2. 因果遮罩为什么必须排除未来位置？
3. 采用 LoRA 是否意味着无需 SFT 数据、模型也会自动记住新政策？

<details><summary>参考答案</summary>

1. 不能。切分依赖分词器，计费还依赖具体服务口径，应实测并记录版本。
2. 自回归位置只能使用允许的前缀信息；算例把未来位置排除，避免把未来当作已知输入。
3. 不是。LoRA 是适配参数的方法，数据与训练目标仍需明确；运行时检索与参数训练是不同机制。
