# Q009 最小 Agent Loop 应包含哪些环节？

**优先级：P0**

## 简要回答

最小闭环是读取目标与状态、请求下一动作、检查动作、执行工具、记录观察，再判断继续或结束。**模型只提出动作，程序负责工具白名单、参数验证、权限和预算。** 每轮都要有可追踪的状态变化；最终答案、等待输入、预算耗尽与不可恢复失败应该是不同终态，便于用户知道是否完成。



## 详细解析

[查看原图](../website/assets/diagrams/concepts/C6-runtime-boundary.png)

沿闭环看本轮输入、动作请求、实际执行与状态更新，循环还需要由运行时决定继续、等待或停止。

先把目标转成可检查的终态，再定义循环读取的状态：用户已给条件、有效证据、待解决问题、操作关联与剩余预算。一次迭代先观察这些信息，请策略提出下一动作；动作可以是调用工具、澄清、等待或结束。策略可能由模型实现，也可以用脚本替身检查控制流，两者能够证明的能力范围不同。

执行前由运行时验证工具集合、参数、可信身份和业务条件，需要的批准也在这里检查。通过后才进入真实工具路径，返回观察并更新状态。决定、尝试和结果应分别记录：决定调用一次，不代表仅有一次底层尝试；模型同时要求多个工具时，还要按调用标识关联结果，检查依赖，不能按返回先后随便拼接。

循环每次都要判断是否继续。证据充分且满足任务合同才完成；缺输入进入等待，权限拒绝或无法恢复的错误结束，预算不足则报告完成项与缺口。工具结果不是天然可信指令，模型建议结束也需要验收。将事件与状态串起来，可以像查派工单一样区分拟办、已受理和已办结，但外部系统状态还需独立核对。只写无限循环会把终止、失败与副作用都藏在循环体里，出了故障就很难解释到底停在哪一步。

## 常见追问

1. **一轮可以有多个工具调用吗？** 可以，模型响应可能包含多个调用。执行器要保留各自标识、结果和错误，检查是否有依赖与副作用冲突；不能因为它们同时出现就默认能够并发，也不能把一份结果配给另一动作。
2. **模型输出最终答案，运行时就直接完成吗？** 先核对任务合同。只读问答要检查必要证据，写任务还要检查后端对象与内容；缺少材料时可以结束并报告未完成，但不能把一个结束字符串当成功证据。
3. **脚本循环测试通过说明什么？** 说明覆盖到的参数、分支和停止合同按预期运行。脚本预设选择与答案，不能证明真实模型能正确理解问题；接入模型后仍需任务集评测工具选择、参数和最终结果。

## 实战案例

以仓库 happy 场景为教学对象：脚本先提出搜索，再给出结束决定。初看 steps=2 容易误读成执行了两次搜索，实际 search_attempts=1。处理时按 decision、observation、stop 逐项对应，确认第二步是结束。验收复核事件、读尝试与对象数，再插入无批准的写建议：执行器应拒绝、实际创建数为零。测试检查控制合同，不把固定脚本输出当作真实模型正确处理政策的证据。



## 常见误区

`while True` 加工具执行就完成系统设计；忽略无进展循环和工具副作用。把工具重试次数、策略步数和模型输出 token 数混成同一个预算，也会让停止条件失去含义。

## 动手想一想

手写六个状态及合法转移。验收：从每个非终态出发，都能解释如何到达完成、等待或失败状态。再给每条转移标出输入事件与状态字段，选一个外部写结果未知的情形，说明为什么不能直接进入成功。
