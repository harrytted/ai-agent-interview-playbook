# Q084 怎样定位 Agent 的延迟瓶颈，为什么加 Worker 未必更快？

**优先级：P0**

## 简要回答

我先画模型与工具的数据依赖图，再记录入队、模型开始、首 token、工具起止和任务终态。只有独立节点才能并行，完整延迟由关键路径和资源限制共同决定。规划 200ms、两路读取 300/500ms、综合 400ms，理想并行下界是 1100ms，串行是 1400ms；真实服务还含排队、限流和重试。应同时看质量、端到端延迟、吞吐与费用，首字快不等于任务完成快。



## 详细解析

先确定计时对象。用户等完整报告，模型服务可能只报首 token，工具平台可能只报单次读取；把这些数直接混在一起会误判。为同一运行记录入队、开始处理、模型调用、首 token、工具起止和最终交付，失败与重试同样保留。统计 p95 时说明是请求、模型调用还是任务，以及未完成任务怎样处理，才有可比较的口径。

再画真实依赖。规划完成后两路读取可独立运行，综合必须等它们都结束，耗时下界为 `200+max(300,500)+400=1100ms`，串行为 `200+300+500+400=1400ms`。这个计算假设固定耗时、无限可用 Worker 和无调度开销。若 B 必须使用 A 返回的对象 ID，就不能套用并行图；多雇一个 Worker 也拿不到尚未产生的输入。

找瓶颈时看资源竞争。增加并发可能挤满数据库连接、搜索配额、模型 token 限额或 KV 容量，引入排队与重试。工具平均耗时降低也可能伴随尾部延迟变差。应分别测在途请求、队列等待、限流和失败，把可并行程度与下游承受能力一起评估；汇总方处理不过来时，用背压暂停新增工作。

优化从一个主要因素开始。可以先并行独立读取，再压缩冗余工具返回或减少不必要模型调用，每次保留相同任务、版本和质量门槛。托管服务要处理配额、429 与退避；自部署还需模型装载、KV 管理与调度。吞吐、首 token、生成速度和任务完成延迟存在取舍，最终选择应符合实际交付目标，而不是只优化最好看的看板。

## 常见追问

1. **为什么线上 p95 大于关键路径？** 下界忽略排队、资源竞争、网络与重试，线上还存在任务差异；应测各阶段分布再定位。
2. **流式输出算不算优化？** 可改善可感知响应时间，但未必缩短完整任务，需分别报告首字与终态时间。
3. **下游限流时继续加并发呢？** 可能增加失败和退避，应限制在途量、按期限排队，必要时减少非关键探索。

## 实战案例

教学案例把两路政策读取改成并行后，数据库连接耗尽，报告反而更慢。处理时保留独立读取，限制共享连接并记录排队时间，综合仍等待必要证据。验收先复算 1100ms 理想下界，再用阶段日志解释实际延迟；比较表包含限流、重试和质量，不把脚本计算的下界写成真实并发测量。



## 常见误区

把独立节点数量当成可无限并发；拿首 token 代表完整延迟；只统计成功请求；把理想 DAG 下界当作线上性能承诺。
