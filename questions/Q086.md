# Q086 多分支 Agent 怎样控制共享预算，并设计模型升级与降级？

**优先级：P0**

## 简要回答

主任务需要共享账本，包含调用量、预估与实际 token、费用和总期限。分支派发前原子预留，结束后结算，重试同样消耗预算，取消后未确认用量不能直接释放。总额 1000，A 预留 600，B 要 500 就应拒绝或重规划。已有输入却抽取/推理失败可升级；用户未提供条件应澄清，资料缺失应补读，真实来源冲突要保留并裁决。降级只能减少合同允许的探索，不能牺牲必要证据或授权检查。



## 详细解析

先把预算定义为整个任务的资源合同。除费用，还要限制模型和工具调用、token、总期限与在途请求。**每个分支不能维护自己的余额副本**；多服务实例需一致性存储或原子预留，保证同时申请时不会超额分配。稳定预留 ID 可识别重放，同 ID 改额度应进入冲突处理，不能重复扣账或静默改变原意。

额度流程包含预留、实际计量、结算和释放。A 预留 600 后总额 1000 只剩 400，B 要 500 应拒绝、缩小或等待。失败和重试也会产生成本；取消只代表控制意图，已提交调用可能继续运行，因此保留待结算用量并与提供方计量对账。局部工具超时重试必须服从主任务剩余期限，不能每次重新领取完整时间。

模型路由先用能验证的触发条件。有限类别分类和字段提取可以尝试轻量路径；完整输入已给、但抽取或联合推理失败时可升级。用户未给关键字段则待澄清，证据未取得则补读，同条件下权威来源真实冲突则待裁决，不能让强模型猜。模型自称有信心不是通用可靠依据；升级后还要核算两次调用、上下文传递和误路由成本。更强模型无法读取尚未入库的条文，数据缺口应补资料而非无限升级。

高负载时用有界队列和背压，在昂贵执行前挡住超量请求。可减少非关键候选或探索，产品允许时交付明确的部分结果；若完整证据是硬要求，就转为未完成或请求补充。评测同时展示质量门槛、成功成本、排队与退步样本。预算控制的目标是让系统遵守合同，不是为了省一次调用就把不确定结论交给用户。

服务容量与预算是两道条件。[Little 定律](../advanced/10-performance-and-serving.md#little-定律连接平均在途量与等待)连接稳定系统内的平均在途数、通过速率和平均停留时间，不能只给到达率就预测等待或 p99。有界拒绝保护本服务；背压还要求上游按反馈减速，立即重试可能放大负载。

## 常见追问

1. **本地字典能做共享预算吗？** 可演示顺序机制，不能支撑多进程原子预留；真实多实例需要共享且一致的控制点。
2. **取消分支为什么不马上释放？** 远端可能尚未停下，立即释放会让新调用与旧费用同时发生，应待确认或按明确规则结算。
3. **小模型输出格式合法就不用升级吗？** 格式只是一个条件。已有材料推理失败可升级；覆盖不足应补读，用户缺参应澄清，真实冲突应保留并请求裁决，不能统一升级或用 schema 通过代替正确。

## 实战案例

教学案例中两个 Worker 都读到余额 1000，各申请 600。处理时改为主任务原子预留，第二笔拒绝后重规划为 400，并给两路传递同一截止时间。验收账本总预留不超过 1000、重放同 ID 不重复扣额、取消中调用保留待结算状态；简单路径缺证据时停止交付并补读，只有材料齐全而能力不足才考虑升级，不能仅给出自信回答。



## 常见误区

每个 Worker 单独限额却认为总额受控；失败调用不计费；取消等于退款；用模型自评分作为唯一升级条件。

## 动手想一想

运行预算实验，写出 600+500 被拒、600+400 被接受的账本，再模拟取消但远端未结束。验收区分预留、已用和待结算，并设计一条升级条件及一条产品允许的降级路径。
