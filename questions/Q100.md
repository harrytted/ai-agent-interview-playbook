# Q100 模型生成的 SQL 怎样限制表列行、写操作和查询资源？

**优先级：P0**

## 简要回答

候选 SQL 不能自己选择身份或高权限连接。宿主先根据可信身份限定可见数据，再限制允许表列、函数和操作，并设置语句大小、执行步骤、期限和返回量。参数绑定保护值输入，不自动约束任意 SQL 结构；只读也不等于租户隔离。SQLite 实验通过租户快照、authorizer 和 query_only 实施具体控制，不冒充 PostgreSQL RLS 或操作系统沙箱。



## 详细解析

执行控制从可信身份开始。用户输入、模型生成字段或自然语言中的“我是管理员”不能直接指定数据库作用域。宿主决定连接、权限和资源合同，候选只提供受约束的查询。参数化绑定日期和 ID 等值，不能因此允许任意表名、连接、函数或无界计算。

配套 SQLite 实验把 alice/bob 测试身份映射到租户，以固定参数化查询从只读源文件复制各自允许行，建立独立内存数据库。候选只能访问快照，不能拿到源连接，所以去掉 WHERE 也读不到另一个租户。源薪资字段不复制。该做法适合小数据实验，有复制与新鲜度代价；服务化时必须用真正认证替换测试映射。

**authorizer** 是 SQLite 编译期授权回调，检查读取表列、函数及操作。实验默认拒绝未允许的访问，即使语句以 WITH 开头，后面的 DELETE 也会被拒绝。候选不能读取内部表、附加别的数据库或加载扩展。只允许 SELECT/WITH 的前缀检查只是入口收窄，执行层回调才处理前缀掩盖的操作。[SQLite authorizer](https://www.sqlite.org/c3ref/set_authorizer.html)

`query_only=ON` 提供连接写入限制，但不会自动控制租户或脱敏列。多个层次应各自验证：行范围由可信快照承担，列/函数由授权回调承担，写入再由只读连接限制。不能把 SQLite 文件模式说成 PostgreSQL 角色或 RLS；数据库方言与实际运行角色不同，保证也不同。

资源层限制 SQL 文本、一个语句、返回行数及执行预算。进度回调按约 100 个 SQLite 虚拟机指令检查步数和期限，非零返回会中断；返回超过预算则报告超限，不将截断数据当完整统计。[进度回调](https://www.sqlite.org/c3ref/progress_handler.html) 这些不是精确 CPU/内存硬限额，也不能防御获得宿主代码执行权的人；生产需要进程与数据库层的额外隔离。

## 常见追问

1. **只读 SQL 为什么还需要预算？** SELECT 可以产生巨大连接、递归或大量返回，仍会消耗资源。只读限制修改，不限制计算与数据量。
2. **越权失败能让模型修复到成功吗？** 应先确认用户有没有相应授权。不能把拒绝当作鼓励绕过的反馈；本实验遇到访问拒绝或资源超限就停止候选循环。
3. **加 LIMIT 是否就避免大扫描？** 不保证。聚合或排序可能先处理大量行再产生少量结果；需要执行预算和实际查询计划，返回行上限只约束结果量。

## 实战案例

alice 候选移除租户过滤后仍只返回 a1/a2/a3，bob 只见 b1；读取快照禁用列、sqlite_master、加载扩展及 WITH 后 DELETE 被拒绝。递归 SUM 超过步数预算被中断，随后正常查询仍能执行。验收检查拒绝原因、返回对象集合和源数据库字节未改变，不只查看 HTTP 或进程成功码。



## 常见误区

让模型传 user/tenant 选择高权限范围；认为参数化已约束任意 SQL；把只读等同隔离；只加结果 LIMIT 就称为计算资源限制。

## 动手想一想

构造一条前缀为 WITH、实际执行 DELETE 的候选，以及一条返回很少但递归计算很多的 SELECT。验收：前者拒绝写，后者受预算中断，之后正常统计仍正确；分别指出哪层控制起作用。
