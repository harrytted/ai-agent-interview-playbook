# Q079 文件系统 Backend、路径白名单和沙箱分别保护什么？

**优先级：P0**

## 简要回答

Backend 决定文件工具读写到哪里，路径规则限制允许访问的对象，沙箱约束代码能接触的文件、网络、进程和资源。**一个虚拟 `/workspace` 或本地目录映射不自动形成隔离**。我的设计会核对实际挂载、身份、出站网络和执行能力，处理规范化、符号链接及检查后变化；依赖安装和测试同样执行代码。凭据尽量留在受控服务，不能因为模型叫“只读助手”就交给它管理员权限。



## 详细解析

先沿一次文件调用找实际落点。工具显示的路径可能对应线程状态、真实本地目录、跨线程存储或远程环境。Backend 解决映射与存储生命周期问题，不能由路径样式推断隔离能力。相同的工作区名称可以接到不同系统；选型时要查看对应后端的实际行为，尤其确认本地 shell 是否直接使用宿主的文件与进程权限。

再定义需要保护的资源。修复任务一般只需指定仓库、临时目录、有限网络和执行额度，工具服务与数据库还要独立检查调用身份。路径控制不能只做字符串前缀判断：规范化后的路径、符号链接和检查后资源变化都可能影响最终目标。需要让真正执行读写的边界落实控制，不能依赖模型在自然语言中承诺不越界。

代码执行范围应覆盖整个任务。测试、构建和安装脚本与 Agent 自己生成的命令一样，都可能访问网络或文件；只审查最后一条命令会留下明显空隙。容器也需具体看宿主挂载、网络、特权与资源配置。隔离强度、启动成本和调试便利存在取舍，可以为不同任务选环境，但必须让可用权限与任务风险匹配。

凭据采用最小范围和有限期限，尽量由受控执行器或服务使用，减少进入上下文、索引、普通日志与任意可读文件。结果输出也要检查，避免环境守住写入却让秘密从日志流出。验证时使用测试目录与测试凭据，检查被拒绝动作及资源状态。评价隔离依据实际访问结果，而不是“用了某框架”这一个配置名。

## 常见追问

1. **文件工具被限制，Bash 也会自动受限吗？** 未必。两种工具可能走不同执行路径，要检查 shell 的身份、挂载与系统权限。
2. **容器是不是足够了？** 要看配置；过宽宿主挂载、特权或网络仍会扩大范围，容器名称不能替代访问测试。
3. **把密钥放环境变量就绝对安全了吗？** 不是。可执行代码可能读取它，日志也可能输出；应控制可见范围、执行主体、有效期和数据出口。

## 实战案例

教学案例允许 Agent 改测试仓库，仓库中的安装脚本却尝试读取另一个目录。处理时仅挂载必要工作区与临时目录，限制出站访问，使用替身凭据，并在执行层检查最终文件目标。验收让正常测试可运行、越界读取被拒绝，敏感测试标记不出现在工具返回和日志；还要验证通过符号链接访问时同样受控。



## 常见误区

把 Backend 当作沙箱；只审查模型生成的脚本，忽略仓库自带安装脚本；把路径字符串过滤当作完整资源隔离。
