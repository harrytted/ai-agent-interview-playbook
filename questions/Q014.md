# Q014 Checkpoint 能保证恢复后不重复扣款吗？

**优先级：P0**

## 简要回答

**Checkpoint（检查点）保存某个执行边界的应用状态。** 能否跨进程恢复，取决于实际使用的持久化后端；仅存内存的检查点会随进程退出丢失。即使状态已持久保存，远端支付与这份记录通常也不是同一事务。如果远端已扣款、确认尚未保存就崩溃，“待支付”不能证明钱没扣。应按稳定业务操作 ID、完整参数及服务的幂等和查询合同确认结果。[持久化参考](https://docs.langchain.com/oss/python/langgraph/persistence)



## 详细解析

先区分两份事实：本地记录执行进度，外部服务记录业务对象。Checkpoint 可以保存已知条件、下一节点、批准和工具结果；恢复可能重新进入某段代码，不表示另一个系统也回到旧状态。

[![本地保存意图、远端提交、本地确认之间的故障窗口](../website/assets/diagrams/G8-write-recovery.png)](../website/assets/diagrams/G8-write-recovery.png)

关键窗口是“远端提交之后、本地确认之前”。提高 checkpoint 频率能减少一部分重做，却不能自行消除两边没有共同事务的窗口。幂等键也需要服务端原子去重、同键异参冲突和可说明的保留期；只在请求里添加一个 ID 没有保护作用。

本仓库用工单代替真实支付：先保存 operation_id 和完整草稿，服务创建对象，本地再记 object_id。恢复沿用原意图查询并核对参数。无法确认时保持未知或转人工，不换新 ID 补一次。

## 常见追问

1. **检查点更细就能保证不重复吗？** 不能仅由细度推出。还要检查外部事务和幂等边界。
2. **幂等是不是只发一次请求？** 请求可以多次；同一意图在服务合同内只产生一份副作用。
3. **同样金额的新付款用旧 ID 吗？** 新独立意图需要新 ID；相同参数不等于同一意图。

## 实战案例

工单崩溃恢复实验用任务数据库保存意图，用服务数据库保存模拟工单，两者没有共同事务。第一进程在服务提交后退出；第二进程用原 operation_id 恢复，核对对象内容。这个实验验证特定本地模拟合同，不承诺所有外部系统 exactly-once。



## 常见误区

把本地快照当成远端事实；把“超时”直接解释为未执行。

## 动手想一想

闭卷画出两个存储与三个时刻，圈出故障窗口。合格回答须说出“不共享事务、原操作 ID、未知结果查询”三点；较好回答还能解释同键异参和保留期。新条件：服务已删除幂等记录、又没有查询接口，此时应暂停或对账，不能据旧 checkpoint 自动重付。轨迹诊断继续做 Q046。
