# Q046 Checkpoint 能保证崩溃恢复后不重复执行工具吗？

**优先级：P0**

[Q014](Q014.md)已经解释故障窗口。本题给出诊断材料，要求指出恢复进程在第5步还不知道什么、第一项应做什么，不能只回答“加幂等”。表中服务记录由事后检查取得，不表示调用方在崩溃前已知道结果。

| 顺序 | 记录方 | 已记录事实 |
| --- | --- | --- |
| 1 | 本地任务数据库 | 已保存创建意图和650元草稿，等待执行 |
| 2 | 调用方 | 首次创建请求已发出 |
| 3 | 模拟服务 | 已按原操作意图创建工单 |
| 4 | 调用方 | 成功回包未保存，进程退出 |
| 5 | 恢复进程 | 本地仍未确认，继续使用原操作标识 |

## 简要回答

先查可观察记录，不能从 checkpoint 的“待执行”推断远端没做。将业务操作 ID、具体尝试和外部对象分开，定位最后一个已确认事实，再用原操作 ID 查询或按幂等合同恢复。Checkpoint 帮助恢复本地状态，外部结果还需单独核对。[持久化参考](https://docs.langchain.com/oss/python/langgraph/persistence)



## 详细解析

按调用方视角读题面：第2行只证明发出请求，第4行说明尚未持久保存确认，第5行因此不能从“待执行”推出远端没做。第3行是事后取得的服务证据，它证明对象已经存在，却仍需核对是否对应当前保存的业务意图和参数。

恢复时先检查当前权限和保存的参数，再按原操作查询；找到工单后核对租户、金额、日期与内容，补写本地确认。只查询“是否存在同标题”不足以确认原意图。若查询暂时为空，也只得到“这次未查到”的观察，是否可用原键重试，仍依赖服务的幂等与可见性合同。

run_id关联任务运行，attempt_id关联一次尝试，operation_id跨重试关联业务意图，object_id指向已经存在的工单。给恢复尝试新编号可以，给同一意图新操作ID会破坏去重。测试以实际对象数与内容验收；若迟到回包与查询同时证明同一对象，再按[Q060](Q060.md)归并确认。

## 常见追问

1. **查询暂无结果就能新建吗？** 需看服务的一致性与幂等合同。暂未可见不必然未提交，不直接换 ID。
2. **权限已撤回怎么办？** 不按旧批准执行未发生的新写入；确认既有结果也要按当前允许范围进行。
3. **恢复后请求又发了一次算失败吗？** 请求数不是唯一判据。检查原意图是否只产生一个符合参数的对象。

## 实战案例

运行“工单崩溃恢复”故障测试：第一个 Python 进程预期以退出码73结束，第二进程读取保留数据库继续。验收时查看原意图、服务对象、连续事件序号，并重复恢复确认没有第二对象。崩溃没有最终 result.json 属于故障本身，不能补写一份伪成功记录。



## 常见误区

只看 checkpoint；把 object_id、operation_id 和尝试编号混用；检查后端数量却不检查对象内容。

## 动手想一想

对上表标出“本地已知、远端事实、需补查”三类信息，写恢复的第一动作与禁止动作。合格回答是原 ID 查询、完整参数核对、禁止新意图重建；较好回答说明暂不可见和权限变化。新条件：查询返回金额800元，应报告冲突并停止，不能因ID相同直接认领成功。
