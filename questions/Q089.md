# Q089 人工审批怎样与参数、恢复、撤销和审计绑定？

**优先级：P0**

[Q043](Q043.md)已定义具体动作的批准合同；本题考撤回同意与写入交错时，哪些动作还能阻止、哪些事实必须保留。以下是设计时间线，不是远端取消实测：

| 时刻 | 已发生的事 |
| --- | --- |
| t1 | 用户批准报告v3上传内部目录，绑定操作`op-7`和完整参数摘要 |
| t2 | 执行器持久提交派发记录，已把请求发往文档服务 |
| t3 | 用户撤回本次批准，并要求停止后续工作 |
| t4 | 文档服务迟到回包：`op-7`已经创建对象`doc-9` |

此时能否只把状态改为“已撤销”就结束？若t4回包丢失，恢复时又应如何处理？

## 简要回答

撤回批准后停止新派发，但t2已发出的动作可能完成。t4必须核对并记录`op-7`对应的`doc-9`，向用户同时说明后续已停、对象已经存在；撤回批准不会自动删除对象。回包丢失则保留结果未知，在当前授权允许的范围内查询原意图，不以新ID补发。删除或补偿是另一项需授权的业务动作，审计要能关联批准版本、撤销、派发和真实结果。



## 详细解析

先把批准状态与执行状态分成两条线。批准可以从有效转为撤回；执行可能已经从待派发走到在途、结果未知或已确认。t3改变了后续允许做什么，不能反向抹掉t2已经发出的请求；t4提供的是外部事实，不能只因它迟到就丢弃。

本地必须定义撤回与派发谁先提交的边界：撤回先提交，阻止新动作；派发先提交，保存停止意图并核对在途结果。两者不能各读一份旧状态后独立宣布获胜。[任务服务](../advanced/16-service-deployment-and-operations.md)以本地事务说明这一边界，远端是否真正接受取消仍看服务合同。只取消聊天输出，不能证明业务写入已停止。

t4到达后，按`op-7`、完整参数和对象版本归并确认；若回包丢失，恢复沿原意图查结果。已撤回的动作不能因一次查询为空就重新创建，查无对象也未必证明在途请求不会稍后完成。若当前资格也被撤回，查询与接管仍须遵守当前授权；本地可以保留已知记录并交给有相应权限的处理路径，不能借“对账”扩大读取范围。

再改变一个分支：若报告在t2之前变成v4或目标改为外部目录，原批准应失效，未派发动作回到待重审。参数摘要要覆盖正文、对象、目的地和工具合同，但不承担认证身份的作用。审批/等待合同见Q043，本地状态与Outbox的双写问题见[Q061](Q061.md)，这里重点是变更发生在哪条状态线上。

审计记录关联任务、主体、批准ID与版本、撤回事件、操作ID、派发记录和后端对象，足以还原上述时间线即可。正文用受控产物指针连接，避免无差别复制敏感内容和凭据。后续删除`doc-9`或发布更正都要记录为新的业务动作，不把修改本地状态当作补偿已经完成。

批准准确绑定参数仍需要[检查与使用的一致性条件](../advanced/11-security-and-governance.md#检查与使用之间也需要一致性条件)。问“撤权从哪个提交边界开始阻止新动作、远程系统是否共享事务、在途结果怎样核对”，比笼统要求执行前再检查一次更能暴露实现缺口。

## 常见追问

1. **t3先于t2提交会怎样？** 在相同本地转换合同下应阻止派发；检查真实记录，而不是按界面显示时间推断执行顺序。
2. **撤回后查询为空，可以用原键再建吗？** 不能仅凭空结果重新创建；原请求可能仍在途。保留未知并按取消与查询合同处理。
3. **用户撤销后远端仍成功怎么办？** 记录真实结果并按业务规则决定后续补偿，不能通过把本地状态改成取消来抹去外部事实。

## 实战案例

沿题面保留两种故障：t4回包到达时确认现有对象，t4丢失时只查询并保留未知。验收检查撤回后没有新增派发、已存在对象未被隐藏、恢复未创建第二个对象，批准和撤回记录都能关联原操作。再将撤回安排在派发提交前，预期外部对象数为0；这是不同的时间条件，不能混成同一条“取消成功”断言。



## 常见误区

会话级 approved=true 永久有效；让模型参数指定审批人；用 hash 替代认证；撤销时清空日志却不处理在途动作。

## 动手想一想

分别将撤回放到派发提交前、提交后回包前、对象确认后三个位置，画批准与执行两条状态线。验收列出允许的新动作、尚未知的事实与后端对象数；增加当前读取资格被撤回的条件，说明如何在允许范围内保存进度或接管，而不是继续用旧权限查询。
