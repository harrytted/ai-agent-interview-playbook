# Q089 人工审批怎样与参数、恢复、撤销和审计绑定？

**优先级：P0**

## 简要回答

审批应绑定可信用户、租户、具体动作、对象、规范化参数摘要、版本和有效期，不能只存 approved=true。执行前重验参数、当前权限与对象状态；内容或目的地变化就重新评估。批准完成和动作完成是两个状态，远端成功而响应丢失时沿原操作 ID 查询或幂等恢复。撤销还要处理运行中与等待恢复任务，审计关联批准、调用和后端对象，同时避免无差别记录敏感正文。



## 详细解析

先把批准对象做具体。上传报告需要记录谁批准、哪个租户、哪份内容、哪个目录、使用什么工具与参数，而不是在整个会话里放一个布尔值。对规范化参数计算摘要可发现变化，但摘要本身不验证签字身份；身份应来自可信会话。遗漏收件人、附件或目标目录，会让批准只覆盖部分动作，后续仍可能改变真实影响范围。

暂停等待时持久保存请求与待执行意图，释放运行资源。批准到来后校验请求版本、审批人当前权限、到期条件及对象状态，再恢复允许动作。模型新增一条“用户已同意”的普通消息不能替代可信批准记录。等待期间内容被编辑、权限被撤销或工具合同改变，都需明确失效或重审路径，避免旧按钮批准新动作。

执行与审批分别记状态。可先记录待写意图与稳定业务操作 ID，再调用具有明确幂等合同的后端，最后登记对象 ID 与终态。若远端已成功、本地未确认，结果应视为未知并查询或用同一键、同一参数恢复，不能改新 ID 重做。幂等解决重复意图，审批解决是否同意，二者互不替代，已经获批的动作同样可能重复执行。

撤销与治理要覆盖正在运行的任务。停用工具、撤销凭据后，停止新派发并重新验证待恢复动作；已经提交的副作用仍需对账。事件关联任务、主体、策略版本、批准 ID、操作 ID 和后端对象，足以解释谁同意什么以及发生了什么即可。敏感正文和凭据不应为了可追溯而无差别保存，审计范围与数据最小化需要同时设计。

## 常见追问

1. **参数 hash 相同就一定可以执行吗？** 不够，还需可信审批身份、有效期、资源状态与当前授权；hash 只帮助绑定内容。
2. **批准前后目标目录变了怎么办？** 原批准不能默认沿用，应重新评估影响范围并按合同重新审批，而非仅修改模型上下文。
3. **用户撤销后远端仍成功怎么办？** 记录真实结果并按业务规则对账或补偿，不能通过把本地状态改成取消来抹去外部事实。

## 实战案例

教学案例用户批准报告 v7 到内部目录，等待期间 Worker 把目标换成外部 URL。执行器核对参数摘要后拒绝原批准并生成待重审状态。另一分支在合法写入后丢失响应，恢复沿同一操作 ID 查询既有对象。验收分别检查未发生越权外发、合法对象仅一份、批准记录和后端 ID 可关联，不把审批成功当作上传成功。



## 常见误区

会话级 approved=true 永久有效；让模型参数指定审批人；用 hash 替代认证；撤销时清空日志却不处理在途动作。

## 动手想一想

为报告 v7 画批准与执行两条状态线，注入过期、改参数、撤权、响应丢失。验收每种情况都有确定恢复分支，并说明哪个状态允许外部写入、哪个状态必须查询结果。
