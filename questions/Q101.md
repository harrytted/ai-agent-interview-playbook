# Q101 SQL 助手怎样有限修复，并用多数据实例核验语义？

**优先级：P0**

## 简要回答

区分语法/字段错误、访问拒绝、资源超限和可执行但口径错误。可修复错误给出受控反馈，总尝试次数与预算预先限制；越权不能靠反复变形通过。业务语义由独立期望和多份数据实例核验，接受等价 SQL，不只比字符串或一次执行成功。策略不能提前读取隐藏标准答案；预制候选通过只证明执行与评分链路，真实模型能力要另设未泄题评测。



## 详细解析

数据库反馈能说明某个列不存在、语法不支持或执行被中断，但通常不知道用户真正想按申请日期还是审批日期统计。先按错误类别决定是否继续：语法、字段和部分方言错误可以尝试修复；访问拒绝需要停止或由用户合法调整授权；资源超限应缩小任务或结束，不无限放大预算。

有限修复需要总尝试数、期限和停止原因。配套实验最多两次候选，执行反馈逐次记录，不因异常重新启动就无界尝试。默认第一份编造列名、第二份使用正确列的轨迹是预制候选，用来检查反馈和上限，不证明语言模型学会修复。另一场景给五份错误候选，仍只执行两份。

**语义核验** 关注结果是否回答了指标合同。只比较 SQL 文本会误伤不同别名、谓词顺序或等价子查询；只看一份数据，又可能让错误查询恰好返回同值。多份实例改变重复金额、连接数量、缺失值和日期，能够暴露部分偶合错误。Distilled Test Suites 论文用一组数据库上的执行结果近似语义准确率；有限测试仍不提供任意等价证明。[论文摘要](https://arxiv.org/abs/2010.02840)

独立期望应在执行后参与评分，不能给生成或修复策略提前看。否则模型只需追逐已知金额，而不用理解查询。实验将三份 fixture 结果保存在独立 expected 文件，执行器和预制候选循环不读取它；测试另外验证等价改写接受、错误日期拒绝。评分通过范围仅覆盖明确数据与合同。

返回表还要连接到文字结论，说明金额单位、可见范围、日期依据、计数和分母。候选零行或金额未知时保留限制，不能生成“现实中不存在”或“全部未超标”。真实模型评测应固定模型/提示/Schema 版本，记录生成 SQL、修复次数、预算、执行结果和费用；本实验外部候选入口只执行文件中的 SQL，不核验其模型来源。

## 常见追问

1. **标准 SQL 不同就一定错吗？** 不是。比较合同所需结果及允许的等价行为，并通过更多反例实例查错；不要要求字符串一致。
2. **评分器为什么可以看预期，修复策略却不可以？** 评分器是独立评估者。若隐藏答案进入策略观察，会泄漏任务结果，得到的成功率无法说明未见任务能力。
3. **一个错误 SQL 场景显示 passed 意味着什么？** 可能表示评分器按设计识别了错误。应读具体断言、候选结果和独立评分状态，不能把测试场景通过等同 SQL 业务通过。

## 实战案例

按审批日期查询仍能运行，却把 11 月才审批的 a1 排除；独立预期发现金额和计数不匹配。SUM DISTINCT 在第一份数据碰巧修好 1350，两个 650 的第二份数据立刻失败；包含未知上限的第三份检验分母。验收保持隐藏预期与策略隔离，报告每份实例结果，不用总分掩盖失败类型。



## 常见误区

把运行成功当业务成功；以字符串对齐代替语义；把隐藏金额放进修复提示；用预制 SQL 通过率宣传模型准确率。

## 动手想一想

提交一份等价改写和一份错误日期 SQL 到 candidate 入口，比较三份数据的 grade。验收：等价实现通过，错误日期失败；另写一份未泄题指标任务，说明如何保留独立期望及真实模型成本记录。
