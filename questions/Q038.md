# Q038 怎样解释 p95 延迟，如何定位慢任务？

**优先级：P0**

## 简要回答

p95 描述指定样本窗口与口径下，约 95% 观测值不超过的延迟，不能当作平均延迟。先明确测的是排队、首字还是任务完成，再沿 trace 拆出检索、模型、工具及重试的关键路径。两路资料都必需时，快的那路先回来，用户仍要等慢的那路，因此并发总耗时不能简单相加。超时和取消也要单列，避免它们从统计中消失。



## 详细解析

先定义时间从哪里开始、到哪里结束。入队到终态、模型开始到首字、工具调用起止是不同指标，样本窗口、请求类别和超时处理也需声明。p95 描述约 95% 观测不超过的值，不是平均数，也不是每次请求的期限保证。分位数实现可能采用 nearest-rank 或插值，比较前要固定算法，避免同一组耗时算出不同结果却以为系统改变。

样本少时尾部估计尤其不稳定。按 nearest-rank，20 个排序耗时的 p95 取第 ceil(20×0.95)=19 个值；十个或二十个样本只能说明这组观察，难以稳定描绘真实长尾。超时、取消和未完成任务应单列状态与数量，不能只留下快速成功的请求。报告 p95 时还需给样本量、统计范围与阶段口径。

定位时沿任务 trace 画关键路径。两个独立且都必需的读取分别 0.8 秒、1.6 秒，合并 0.2 秒，忽略调度开销，串行为 2.6 秒，并行为 1.8 秒。慢分支决定等待，而存在数据依赖的工具不能并行。组件耗时分布与相关性会影响整体，因此不能把各组件 p95 相加，当作准确的端到端 p95。

优化要回到相同任务集比较。减少串行调用、缩短上下文、缓存或增加并发，都可能转移瓶颈或损害证据完整性。记录排队、限流、重试与模型阶段，检查慢任务集中在哪类路径。首字快可以改善等待感，但用户要的工单或报告尚未完成时，不能宣布整个任务已经变快。

## 常见追问

1. **各组件 p95 相加为什么不准确？** 各组件的慢请求未必是同一批，还可能并行；需要端到端样本和真实依赖来计算。
2. **超时样本没有终态耗时怎么办？** 单列超时数量、阈值和统计规则，必要时说明观测被截断，不能直接删除后称为全量分布。
3. **并发一定缩短延迟吗？** 只对独立工作有机会获益，下游资源竞争与限流可能增加排队，所以要测真实路径和质量。

## 实战案例

教学案例新版本流式首字更快，但后台搜索重试增加，完整报告更晚。处理时把首字和终态分别计时，关联两路工具的排队与结束事件。验收报表能显示用户等待落在哪一阶段，保留超时与取消数量；2.6 秒和 1.8 秒只作为教学依赖算例，不能替代线上实测 p95。



## 常见误区

首 token 快就宣称任务快；拿十个样本的 p95 给出稳定生产结论。

## 动手想一想

两个独立必要工具分别耗时 0.8 秒、1.6 秒，合并耗时 0.2 秒。忽略调度开销，串行与并发分别需多久？自检：2.6 秒、1.8 秒；再解释为什么这不是线上 p95 的预测值。验收列出两种耗时公式、依赖假设和三个遗漏的真实开销，再说明至少需要怎样的样本与统计口径才能讨论线上长尾。
