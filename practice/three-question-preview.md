# 三题试读：检查 Agent 工程中的三个薄弱点

先用三道题体验本手册的练习方式：判断证据、处理写入失败、设计系统边界。无需安装软件或配置模型密钥。每题先用一分钟口述自己的做法，再展开短答与追问，最后按需要进入完整解析或学习章节。

## 第一题：引用存在，回答为什么仍会错？

一个检索增强生成（RAG）助手回答了住宿标准问题，还附上能打开的制度链接。你核对后发现结论错了：它使用了旧版制度，或者套用了另一类员工的标准。你会从哪里开始排查？

先想一想：链接真实，是否就说明证据支持结论？直接换一个向量模型，能验证哪一种猜测？

<details>
<summary>查看短答与追问参考</summary>

**短答：** 先核对原文、适用日期、人员类别和权限，再沿解析、索引、召回、上下文到生成寻找最早偏差。链接存在不等于证据支持结论；可以用人工确认的正确证据做对照，每次只改一个关键环节。

**追问：换成正确材料后就答对了，能直接认定是 embedding（向量表示）的问题吗？**

不能。这个对照说明原先的证据链路值得排查，但解析、分块、版本过滤、召回、重排和上下文拼接都可能影响最终材料。还需检查各阶段的输入、输出，找到正确证据第一次丢失或被替换的位置，再验证具体原因。

</details>

## 第二题：创建工单超时，能不能再发一次？

Agent 调用“创建工单”工具，等了十秒没有收到响应。此时服务端可能已经创建成功，只是响应没有送回。你会怎样继续，才能避免同一份申请变成两张工单？

先想一想：超时究竟证明了什么？如果再试一次，哪些标识和参数必须保持一致？

<details>
<summary>查看短答与追问参考</summary>

**短答：** 超时只说明调用方没拿到结果，服务端可能已经完成写入。同一创建意图应保留稳定操作 ID，沿原操作查询或按服务端幂等合同恢复；换新 ID 补发可能创建两张工单。无法确认远端结果时，应保留“结果未知”，暂停并对账，必要时转人工处理。

**追问：已经有本地去重表，为什么仍不能保证远端只创建一个对象？**

远端写入成功与本地记录完成可能发生在两个不同的提交边界，中间崩溃就会留下确认缺口。本地表不能单独替远端保证幂等；采用服务端幂等方案时，去重记录与业务写入应具备原子性或等效一致性，并校验同一操作 ID 的参数。第三方不提供安全重复语义时，应通过结果查询、对账或人工处理缩小不确定范围；查询暂时没有结果，也不能直接认定远端未执行并换新 ID 创建。

</details>

## 第三题：设计企业知识库 Agent，应该从哪里开始？

你要为企业做一个知识库客服 Agent：员工能查询制度，特定操作还会创建业务对象。不同员工可见的资料不同，权限也可能随时变更。你会先选技术组件，还是先明确系统需要遵守的条件？

先想一想：谁能看什么、谁能做什么，应该在哪些步骤检查？怎样判断系统完成了任务？

<details>
<summary>查看短答与追问参考</summary>

**短答：** 先明确用户身份、资料可见范围、读写权限和验收目标，再选择技术组件。问答路径包括授权检索、证据筛选和引用核验，写操作则单独检查对象权限、业务状态和具体批准。评测同时检查正确回答、缺证澄清、权限隔离和实际业务结果。

**追问：用户权限刚被撤回，但昨天的答案缓存命中了，还能直接返回吗？**

不能直接返回。缓存命中也要按当前身份和权限重新检查资料可见性；缓存键、失效机制与权限变化需要一起设计。如果答案依赖的材料已经不可见，就应停止使用该缓存，按当前授权重新检索，或说明无法提供相关内容。

</details>

| 分数 | 你现在能做到什么 |
| --- | --- |

| 1 | 看过提示后能解释 |
| 2 | 不看答案，也能独立说清步骤和理由 |
